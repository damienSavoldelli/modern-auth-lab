# v0.8.0 Passkey / WebAuthn Foundation Implementation Notes

This note describes how the `v0.8.0 - Passkey / WebAuthn Foundation` milestone should be approached.

The goal is to add WebAuthn primitives and Passkey enrollment for existing users without replacing TOTP and without introducing public signup.

## Learning Objective

At the end of this milestone, the project should make these concepts clear:

- what a Passkey is and how it differs from a password or TOTP secret;
- why WebAuthn uses public-key cryptography instead of shared secrets;
- why the server stores public credential material, not the private key;
- why challenge generation and challenge expiration are security-critical;
- why origin and RP ID validation protect against phishing;
- why user presence and user verification matter;
- why one user can have several Passkeys;
- why platform, roaming, synced, device-bound, and cross-device usages can share the same server-side WebAuthn model;
- why Passkey enrollment is not the same thing as user signup.

## Current Starting Point

`v0.7.0` provides:

- password authentication;
- full session login state;
- TOTP enrollment;
- Password + TOTP login;
- TOTP lifecycle management;
- recovery-code foundation;
- account security page.

This means `v0.8.0` should not rebuild the account model or TOTP lifecycle. It should add a WebAuthn foundation that can later be connected to the Password + Passkey login flow.

## Product Boundary

This milestone is about Passkey enrollment for an existing account.

It does not implement public signup.

Expected entry point:

```text
existing user
  -> password + TOTP login
  -> fully authenticated session
  -> /account/security
  -> add Passkey
```

The WebAuthn standard uses the word "registration" for creating a credential. In these notes, the project uses "Passkey enrollment" to avoid confusing it with account signup.

## Mental Model

With TOTP, the server and authenticator app share a secret:

```text
Server stores protected TOTP secret
Authenticator app stores same TOTP secret
Both calculate the same code for the same time step
```

With Passkeys, the server stores a public key and the authenticator keeps the private key:

```text
Server stores public key
Authenticator stores private key
Authenticator signs server challenge
Server verifies signature with public key
```

Security implication:

- a database leak of WebAuthn public keys does not give attackers the private signing keys;
- a fake domain cannot normally obtain a valid assertion for the real RP ID;
- the server must still validate every response carefully.

## Supported Authenticator Cases

The implementation should be generic enough to support these cases when the browser and authenticator allow them:

| Case                    | Example                               | Server-side model                                      |
| ----------------------- | ------------------------------------- | ------------------------------------------------------ |
| Platform authenticator  | Touch ID, Face ID, Windows Hello      | WebAuthn credential owned by the user                  |
| Roaming authenticator   | YubiKey, Titan Security Key           | WebAuthn credential with possible USB/NFC/BLE hints    |
| Synced credential       | iCloud Keychain, Google Password Mgr  | WebAuthn credential possibly available on many devices |
| Device-bound credential | Hardware key or local-only credential | WebAuthn credential tied to one authenticator          |
| Cross-device usage      | Desktop login approved from phone     | Normal WebAuthn assertion returned through browser     |

The first implementation should not force the user to choose one of these categories manually. The browser should present the available options. The server should store useful metadata without pretending it can always know whether a credential is synced or device-bound.

## Recommended Step Order

### Step 1: WebAuthn Terminology And Configuration

Define the project vocabulary and configuration boundary before writing verification code.

Expected behavior:

- document RP ID, origin, challenge, credential id, public key, attestation, assertion, user presence, and user verification;
- define local development values;
- decide where WebAuthn configuration will live;
- keep configuration explicit and testable.

Security focus:

- origin and RP ID must be server-controlled;
- challenge lifetime must be short;
- browser-provided data must not be trusted until verified server-side;
- development configuration must not silently become production policy.

Expected areas:

- `docs/concepts/passkeys.md`;
- `docs/implementation-notes/v0.8-passkey-webauthn-foundation.md`;
- `docs/decisions/`;
- future `src/Security/WebAuthn/`.

#### Step 1.1: Vocabulary And Flow Documentation

This sub-step is documentation-first.

It should explain:

- Passkey enrollment vs account signup;
- browser WebAuthn API responsibility;
- server-side verification responsibility;
- why several authenticator types can use the same WebAuthn server model.

Stop after this sub-step and validate the model before adding dependencies or persistence.

Implemented documentation:

- `docs/concepts/passkeys.md`
  - adds a WebAuthn vocabulary table;
  - explains RP ID and origin;
  - explains challenge purpose and expected lifecycle;
  - distinguishes attestation from assertion;
  - distinguishes user presence from user verification;
  - explains transport hints and why they should not become authorization policy by themselves.
- `docs/implementation-notes/v0.8-passkey-webauthn-foundation.md`
  - records the step plan before code is introduced.

Why this matters before code:

- WebAuthn names are close enough to be confusing, especially "registration" vs account signup;
- the backend must eventually validate fields that come from browser ceremonies;
- the frontend can start browser ceremonies, but it cannot prove security properties alone;
- the storage model depends on these terms, especially credential id, public key, sign counter, transports, and revocation state.

What remains after Step 1.1:

- choose the PHP WebAuthn verification library and define the local abstraction boundary;
- decide the first local WebAuthn configuration shape;
- add persistence only after the library boundary is clear.

### Step 2: Dependency And Library Boundary

Choose how the project will verify WebAuthn responses.

Expected behavior:

- prefer a proven WebAuthn library over hand-rolled cryptographic parsing;
- isolate the library behind local application/security classes;
- document why the dependency is justified;
- avoid leaking library-specific objects through controllers.

Security focus:

- WebAuthn verification is security-sensitive and easy to implement incorrectly;
- dependency choice must consider maintenance, PHP version support, testability, and standards coverage;
- the project should remain lightweight, but not hand-roll complex cryptography.

Expected areas:

- `composer.json`;
- `src/Security/WebAuthn/`;
- `tests/Security/WebAuthn/`;
- possible ADR for the dependency decision.

Implemented decision:

- `web-auth/webauthn-lib` is added as the backend WebAuthn dependency;
- the project explicitly requires `ext-json` and `ext-openssl` because the WebAuthn dependency and verification flow depend on JSON and cryptographic operations;
- ADR `0020 - WebAuthn Library Boundary` records why the project uses a maintained library instead of hand-rolled WebAuthn parsing;
- `tests/Platform/WebAuthnDependencyTest.php` checks that the core library classes expected by the future boundary are available.

Why this dependency is justified:

- WebAuthn verification includes CBOR parsing, COSE key handling, client data validation, authenticator data validation, and signature verification;
- implementing this locally would create security risk and distract from the project objective;
- the library still does not decide the project's security policy;
- local services will define allowed origins, RP ID, challenge lifetime, user verification policy, event logging, and fallback behavior.

Important architecture rule:

- controllers should call project-owned application services;
- application services may call project-owned WebAuthn security services;
- project-owned WebAuthn security services may wrap `web-auth/webauthn-lib`;
- controllers should not directly construct or validate library ceremonies.

Code map:

- `composer.json`
  - adds `web-auth/webauthn-lib`;
  - makes JSON and OpenSSL extension requirements explicit.
- `composer.lock`
  - locks the WebAuthn library and its transitive dependencies.
- `docs/decisions/0020-webauthn-library-boundary.md`
  - explains the dependency and boundary decision.
- `tests/Platform/WebAuthnDependencyTest.php`
  - verifies that the expected core dependency classes are autoloadable.

What remains after Step 2:

- define the first WebAuthn configuration object;
- add challenge persistence;
- build enrollment options through a local service;
- keep using the library only through project-owned boundaries.

### Step 3: Credential Storage Model

Add persistence for user Passkey credentials.

Expected behavior:

- one user can have multiple Passkeys;
- each credential stores its credential id, public key material, sign counter, name, transports when available, timestamps, and revocation state;
- credential ids must be unique;
- revoked credentials remain auditable.

Security focus:

- private keys are never stored by the server;
- public keys and credential ids are still authentication material and must be handled carefully;
- revocation should disable one credential without deleting account history.

Expected areas:

- SQLite migration;
- `src/Infrastructure/Persistence/UserPasskeyCredential.php`;
- `src/Infrastructure/Persistence/UserPasskeyCredentialRepository.php`;
- repository tests.

Implemented storage model:

- `user_passkey_credentials` stores one row per Passkey credential;
- one user can have multiple active Passkeys;
- `credential_id` is globally unique because a WebAuthn credential id identifies one credential;
- `public_key` stores verified public key material prepared by the future WebAuthn boundary;
- `sign_count` stores the latest authenticator signature counter when the authenticator provides useful counter behavior;
- `name` stores a user-facing label such as "MacBook Touch ID" or "YubiKey";
- `transports_json` stores browser-reported transport hints such as `internal`, `usb`, `nfc`, `ble`, or `hybrid`;
- `attestation_type` and `aaguid` are nullable metadata fields for future policy and troubleshooting;
- `status`, `last_used_at`, and `revoked_at` support lifecycle management and auditability.

Why there is no private key column:

- the private key must remain inside the authenticator, keychain, phone, password manager, or hardware security key;
- the server only needs the public key to verify future signatures;
- storing private-key-like material server-side would break the core WebAuthn security model.

Why revoked credentials are kept:

- deleting rows would erase security history;
- revocation should disable one credential while preserving when it existed and when it was revoked;
- later account-security pages can show revocation history without exposing secret material.

Code map:

- `src/Infrastructure/Persistence/Migrations/CreateUserPasskeyCredentialsTable.php`
  - creates the Passkey credential table and lookup indexes.
- `src/Infrastructure/Persistence/UserPasskeyCredential.php`
  - immutable persistence model for one Passkey credential.
- `src/Infrastructure/Persistence/UserPasskeyCredentialRepository.php`
  - creates, loads, updates last use, and revokes Passkey credentials.
- `public/index.php`
  - registers the migration in application startup.
- `tests/Infrastructure/Persistence/Migrations/CreateUserPasskeyCredentialsTableTest.php`
  - validates schema columns and core constraints.
- `tests/Infrastructure/Persistence/UserPasskeyCredentialRepositoryTest.php`
  - validates repository behavior, multi-Passkey support, last-used tracking, and revocation.

What this does not implement yet:

- generating WebAuthn enrollment options;
- verifying WebAuthn attestation responses;
- calling `navigator.credentials.create()`;
- displaying Passkeys in `/account/security`;
- using Passkeys during login.

### Step 4: Passkey Enrollment Challenge

Generate the server-side challenge used to create a new Passkey.

Expected behavior:

- fully authenticated user requests a Passkey enrollment challenge;
- server creates a random challenge;
- challenge is stored server-side with an expiration;
- response includes options needed by `navigator.credentials.create()`.

Security focus:

- challenge must be unpredictable;
- challenge must be tied to the current user and session;
- expired or reused challenges must be rejected;
- user id exposed to WebAuthn should avoid unnecessary personal data.

Expected areas:

- `src/Application/WebAuthn/`;
- `src/Security/WebAuthn/`;
- `src/Http/Controller/`;
- backend tests.

Implemented challenge foundation:

- `WebAuthnConfig` defines local relying-party configuration from environment values;
- `Base64Url` provides deterministic unpadded Base64URL encoding for WebAuthn JSON fields;
- `webauthn_challenges` stores short-lived enrollment or authentication challenges separately from durable credentials;
- `WebAuthnChallengeRepository` creates, finds, and consumes challenges;
- `PasskeyEnrollmentChallengeService` creates an enrollment challenge and returns JSON-ready `publicKey` options for future `navigator.credentials.create()`;
- `.env.example` documents local WebAuthn configuration values.

Initial local configuration:

```env
WEBAUTHN_RP_ID=127.0.0.1
WEBAUTHN_RP_NAME="Modern Auth Lab"
WEBAUTHN_ALLOWED_ORIGINS=http://127.0.0.1:8080
WEBAUTHN_CHALLENGE_TTL_SECONDS=300
WEBAUTHN_TIMEOUT_MS=60000
WEBAUTHN_USER_VERIFICATION=preferred
```

Why the challenge is stored:

- the browser response must later prove it answered a challenge the server really issued;
- the challenge must be tied to a user and purpose;
- the challenge must expire;
- the challenge must be consumed after successful verification to prevent replay.

Why Base64URL is needed:

- WebAuthn browser APIs use binary values such as `ArrayBuffer`;
- JSON endpoints cannot carry raw binary safely;
- unpadded Base64URL is a stable text representation that works well in JSON and URLs.

Why `attestation` starts as `none`:

- the current milestone focuses on Passkey enrollment mechanics, not strict authenticator provenance policy;
- strict attestation introduces device/vendor trust decisions that are better handled after the base WebAuthn flow is working;
- the server still verifies the WebAuthn ceremony and stores the resulting public credential material.

Code map:

- `src/Security/WebAuthn/Base64Url.php`
  - encodes and decodes unpadded Base64URL values.
- `src/Security/WebAuthn/WebAuthnConfig.php`
  - validates RP ID, RP name, allowed origins, challenge TTL, timeout, and user verification policy.
- `src/Infrastructure/Persistence/Migrations/CreateWebAuthnChallengesTable.php`
  - creates temporary challenge storage.
- `src/Infrastructure/Persistence/WebAuthnChallenge.php`
  - immutable challenge persistence model.
- `src/Infrastructure/Persistence/WebAuthnChallengeRepository.php`
  - creates, finds, and consumes challenge records.
- `src/Application/WebAuthn/PasskeyEnrollmentChallengeService.php`
  - generates enrollment challenges and browser-facing creation options.
- `src/Application/WebAuthn/PasskeyEnrollmentChallengeResult.php`
  - carries the stored challenge and JSON-ready options.
- `public/index.php`
  - registers the challenge migration.
- `tests/Security/WebAuthn/`
  - validates Base64URL and configuration behavior.
- `tests/Infrastructure/Persistence/`
  - validates challenge schema and repository behavior.
- `tests/Application/WebAuthn/`
  - validates generated enrollment options and exclude-credential behavior.

What this does not implement yet:

- HTTP routes for requesting the challenge;
- frontend JavaScript conversion from Base64URL strings to `ArrayBuffer`;
- `navigator.credentials.create()`;
- server-side attestation verification;
- storing a real verified credential from a browser response.

### Step 5: Browser Enrollment Module

Add focused vanilla JavaScript for calling the browser WebAuthn API.

Expected behavior:

- detect whether WebAuthn appears available for UX only;
- call `navigator.credentials.create()`;
- encode/decode binary WebAuthn data safely;
- submit the browser result to the server.

Security focus:

- frontend capability detection must not decide authorization;
- browser output must be verified server-side;
- binary data conversion must be deterministic and tested.

Expected areas:

- `assets/js/`;
- `tests/frontend/`;
- Vite build.

Implemented browser module:

- `assets/js/webauthn/encoding.js`
  - converts unpadded Base64URL strings from server JSON into `ArrayBuffer`;
  - converts browser `ArrayBuffer` values back into unpadded Base64URL strings.
- `assets/js/webauthn/passkey-enrollment.js`
  - detects whether the current browser context appears to expose WebAuthn;
  - normalizes server-provided creation options for `navigator.credentials.create()`;
  - calls the browser WebAuthn API;
  - serializes the created public-key credential for future server submission.
- `tests/frontend/webauthn/encoding.test.js`
  - validates deterministic binary/text conversion.
- `tests/frontend/webauthn/passkey-enrollment.test.js`
  - validates availability detection, option normalization, credential serialization, and browser API invocation.

Why this step is frontend-only:

- the server already produces JSON-ready creation options in Step 4;
- the browser API needs binary fields as `ArrayBuffer`, not plain JSON strings;
- Vitest can validate our conversion and orchestration without requiring a real authenticator device;
- a real manual Passkey test will only become possible after HTTP routes and server-side attestation verification exist.

Security boundary:

- frontend feature detection is only UX;
- frontend serialization is only transport formatting;
- the browser response is untrusted until the server verifies challenge, origin, RP ID, user presence, user verification, and attestation data;
- JavaScript must not decide whether a user is allowed to enroll a Passkey.

What this does not implement yet:

- rendering a button on `/account/security`;
- fetching enrollment options from the backend;
- posting the browser response to the backend;
- server-side attestation verification;
- storing a real browser-created credential.

### Step 6: Passkey Enrollment Verification

Verify the WebAuthn registration response and store the credential.

Expected behavior:

- validate challenge;
- validate origin;
- validate RP ID;
- require user presence;
- require or document user verification policy;
- store verified credential material;
- add a security event.

Security focus:

- never trust client-provided registration data without server verification;
- prevent replayed challenge responses;
- keep error messages generic in user-facing output;
- log security-relevant success and failure events without logging secret-like payloads.

Expected areas:

- `src/Application/WebAuthn/`;
- `src/Security/WebAuthn/`;
- `src/Infrastructure/Persistence/`;
- `tests/Application/WebAuthn/`;
- `tests/Http/Controller/`.

Implemented verification boundary:

- `PasskeyAttestationVerifier`
  - project-owned interface for WebAuthn attestation verification;
  - keeps application services independent from the third-party library API.
- `WebAuthnLibPasskeyAttestationVerifier`
  - adapts `web-auth/webauthn-lib`;
  - decodes the browser credential payload;
  - rebuilds the expected WebAuthn creation options;
  - verifies challenge, allowed origin, RP ID hash, user presence, user verification policy, attestation format, algorithm, and credential data through the library ceremony.
- `VerifiedPasskeyCredential`
  - project-owned value object carrying verified credential material encoded for persistence.
- `PasskeyEnrollmentVerificationService`
  - checks that the enrollment challenge exists;
  - rejects expired challenges;
  - calls the attestation verifier;
  - stores the verified credential;
  - consumes the challenge after successful storage.
- `PasskeyEnrollmentVerificationResult`
  - returns the stored credential.

Why there are two layers:

```text
Application service
  owns project workflow
  - challenge exists
  - challenge not expired
  - credential name
  - challenge consumption
  - persistence

Security verifier
  owns WebAuthn protocol verification
  - browser payload decoding
  - challenge comparison
  - origin validation
  - RP ID hash validation
  - user presence / verification checks
  - attestation response validation
```

Security implications:

- a browser response is not trusted just because JavaScript produced it;
- the stored Passkey credential is written only after server-side WebAuthn verification succeeds;
- consumed challenges cannot be reused for another enrollment;
- expired challenges fail closed;
- credential public key material is stored, but the private key remains outside the server.

Code map:

- `src/Security/WebAuthn/PasskeyAttestationVerifier.php`
  - local verification contract.
- `src/Security/WebAuthn/WebAuthnLibPasskeyAttestationVerifier.php`
  - WebAuthn library adapter.
- `src/Security/WebAuthn/VerifiedPasskeyCredential.php`
  - verified credential DTO.
- `src/Application/WebAuthn/PasskeyEnrollmentVerificationService.php`
  - application workflow for verified enrollment.
- `src/Application/WebAuthn/PasskeyEnrollmentVerificationResult.php`
  - application result DTO.
- `tests/Application/WebAuthn/PasskeyEnrollmentVerificationServiceTest.php`
  - tests project workflow with a fake verifier.
- `tests/Security/WebAuthn/WebAuthnLibPasskeyAttestationVerifierTest.php`
  - verifies that invalid browser payloads fail at the library adapter boundary.

What this does not implement yet:

- HTTP route wiring;
- real manual browser enrollment;
- account-security UI button;
- security events for enrollment success/failure;
- complete authentication assertion verification.

### Step 7: Authentication Challenge Primitive

Prepare the challenge used later by Password + Passkey login.

Expected behavior:

- generate an authentication challenge for a known user;
- restrict allowed credential ids to that user's active credentials;
- store the challenge with expiration;
- return options for `navigator.credentials.get()`.

Security focus:

- this step prepares v0.9 but does not complete the login flow;
- challenge state must be separate from enrollment challenge state when needed;
- revoked credentials must not be offered.

Expected areas:

- `src/Application/WebAuthn/`;
- `src/Security/WebAuthn/`;
- `tests/Application/WebAuthn/`.

## Out Of Scope

`v0.8.0` should not implement:

- public signup;
- passwordless login;
- replacing TOTP;
- complete Password + Passkey login;
- trusted devices;
- Passkey recovery;
- complex multi-Passkey management UI;
- production attestation policy beyond the documented baseline.
