# v0.8.0 Passkey / WebAuthn Foundation Implementation Notes

This note describes how the `v0.8.0 - Passkey / WebAuthn Foundation` milestone should be approached.

The goal is to add WebAuthn primitives and Passkey enrollment for existing users without replacing TOTP and without introducing public signup.

## Learning Objective

At the end of this milestone, the project should make these concepts clear:

- what a Passkey is and how it differs from a password or TOTP secret;
- why WebAuthn uses public-key cryptography instead of shared secrets;
- why the server stores public credential material, not the private key;
- why challenge generation and challenge expiration are security-critical;
- why origin and RP ID validation protect against phishing;
- why user presence and user verification matter;
- why one user can have several Passkeys;
- why platform, roaming, synced, device-bound, and cross-device usages can share the same server-side WebAuthn model;
- why Passkey enrollment is not the same thing as user signup.

## Current Starting Point

`v0.7.0` provides:

- password authentication;
- full session login state;
- TOTP enrollment;
- Password + TOTP login;
- TOTP lifecycle management;
- recovery-code foundation;
- account security page.

This means `v0.8.0` should not rebuild the account model or TOTP lifecycle. It should add a WebAuthn foundation that can later be connected to the Password + Passkey login flow.

## Product Boundary

This milestone is about Passkey enrollment for an existing account.

It does not implement public signup.

Expected entry point:

```text
existing user
  -> password + TOTP login
  -> fully authenticated session
  -> /account/security
  -> add Passkey
```

The WebAuthn standard uses the word "registration" for creating a credential. In these notes, the project uses "Passkey enrollment" to avoid confusing it with account signup.

## Mental Model

With TOTP, the server and authenticator app share a secret:

```text
Server stores protected TOTP secret
Authenticator app stores same TOTP secret
Both calculate the same code for the same time step
```

With Passkeys, the server stores a public key and the authenticator keeps the private key:

```text
Server stores public key
Authenticator stores private key
Authenticator signs server challenge
Server verifies signature with public key
```

Security implication:

- a database leak of WebAuthn public keys does not give attackers the private signing keys;
- a fake domain cannot normally obtain a valid assertion for the real RP ID;
- the server must still validate every response carefully.

## Supported Authenticator Cases

The implementation should be generic enough to support these cases when the browser and authenticator allow them:

| Case                    | Example                               | Server-side model                                      |
| ----------------------- | ------------------------------------- | ------------------------------------------------------ |
| Platform authenticator  | Touch ID, Face ID, Windows Hello      | WebAuthn credential owned by the user                  |
| Roaming authenticator   | YubiKey, Titan Security Key           | WebAuthn credential with possible USB/NFC/BLE hints    |
| Synced credential       | iCloud Keychain, Google Password Mgr  | WebAuthn credential possibly available on many devices |
| Device-bound credential | Hardware key or local-only credential | WebAuthn credential tied to one authenticator          |
| Cross-device usage      | Desktop login approved from phone     | Normal WebAuthn assertion returned through browser     |

The first implementation should not force the user to choose one of these categories manually. The browser should present the available options. The server should store useful metadata without pretending it can always know whether a credential is synced or device-bound.

## Recommended Step Order

### Step 1: WebAuthn Terminology And Configuration

Define the project vocabulary and configuration boundary before writing verification code.

Expected behavior:

- document RP ID, origin, challenge, credential id, public key, attestation, assertion, user presence, and user verification;
- define local development values;
- decide where WebAuthn configuration will live;
- keep configuration explicit and testable.

Security focus:

- origin and RP ID must be server-controlled;
- challenge lifetime must be short;
- browser-provided data must not be trusted until verified server-side;
- development configuration must not silently become production policy.

Expected areas:

- `docs/concepts/passkeys.md`;
- `docs/implementation-notes/v0.8-passkey-webauthn-foundation.md`;
- `docs/decisions/`;
- future `src/Security/WebAuthn/`.

#### Step 1.1: Vocabulary And Flow Documentation

This sub-step is documentation-first.

It should explain:

- Passkey enrollment vs account signup;
- browser WebAuthn API responsibility;
- server-side verification responsibility;
- why several authenticator types can use the same WebAuthn server model.

Stop after this sub-step and validate the model before adding dependencies or persistence.

Implemented documentation:

- `docs/concepts/passkeys.md`
  - adds a WebAuthn vocabulary table;
  - explains RP ID and origin;
  - explains challenge purpose and expected lifecycle;
  - distinguishes attestation from assertion;
  - distinguishes user presence from user verification;
  - explains transport hints and why they should not become authorization policy by themselves.
- `docs/implementation-notes/v0.8-passkey-webauthn-foundation.md`
  - records the step plan before code is introduced.

Why this matters before code:

- WebAuthn names are close enough to be confusing, especially "registration" vs account signup;
- the backend must eventually validate fields that come from browser ceremonies;
- the frontend can start browser ceremonies, but it cannot prove security properties alone;
- the storage model depends on these terms, especially credential id, public key, sign counter, transports, and revocation state.

What remains after Step 1.1:

- choose the PHP WebAuthn verification library and define the local abstraction boundary;
- decide the first local WebAuthn configuration shape;
- add persistence only after the library boundary is clear.

### Step 2: Dependency And Library Boundary

Choose how the project will verify WebAuthn responses.

Expected behavior:

- prefer a proven WebAuthn library over hand-rolled cryptographic parsing;
- isolate the library behind local application/security classes;
- document why the dependency is justified;
- avoid leaking library-specific objects through controllers.

Security focus:

- WebAuthn verification is security-sensitive and easy to implement incorrectly;
- dependency choice must consider maintenance, PHP version support, testability, and standards coverage;
- the project should remain lightweight, but not hand-roll complex cryptography.

Expected areas:

- `composer.json`;
- `src/Security/WebAuthn/`;
- `tests/Security/WebAuthn/`;
- possible ADR for the dependency decision.

### Step 3: Credential Storage Model

Add persistence for user Passkey credentials.

Expected behavior:

- one user can have multiple Passkeys;
- each credential stores its credential id, public key material, sign counter, name, transports when available, timestamps, and revocation state;
- credential ids must be unique;
- revoked credentials remain auditable.

Security focus:

- private keys are never stored by the server;
- public keys and credential ids are still authentication material and must be handled carefully;
- revocation should disable one credential without deleting account history.

Expected areas:

- SQLite migration;
- `src/Infrastructure/Persistence/UserPasskeyCredential.php`;
- `src/Infrastructure/Persistence/UserPasskeyCredentialRepository.php`;
- repository tests.

### Step 4: Passkey Enrollment Challenge

Generate the server-side challenge used to create a new Passkey.

Expected behavior:

- fully authenticated user requests a Passkey enrollment challenge;
- server creates a random challenge;
- challenge is stored server-side with an expiration;
- response includes options needed by `navigator.credentials.create()`.

Security focus:

- challenge must be unpredictable;
- challenge must be tied to the current user and session;
- expired or reused challenges must be rejected;
- user id exposed to WebAuthn should avoid unnecessary personal data.

Expected areas:

- `src/Application/WebAuthn/`;
- `src/Security/WebAuthn/`;
- `src/Http/Controller/`;
- backend tests.

### Step 5: Browser Enrollment Module

Add focused vanilla JavaScript for calling the browser WebAuthn API.

Expected behavior:

- detect whether WebAuthn appears available for UX only;
- call `navigator.credentials.create()`;
- encode/decode binary WebAuthn data safely;
- submit the browser result to the server.

Security focus:

- frontend capability detection must not decide authorization;
- browser output must be verified server-side;
- binary data conversion must be deterministic and tested.

Expected areas:

- `resources/js/`;
- `tests/frontend/`;
- Vite build.

### Step 6: Passkey Enrollment Verification

Verify the WebAuthn registration response and store the credential.

Expected behavior:

- validate challenge;
- validate origin;
- validate RP ID;
- require user presence;
- require or document user verification policy;
- store verified credential material;
- add a security event.

Security focus:

- never trust client-provided registration data without server verification;
- prevent replayed challenge responses;
- keep error messages generic in user-facing output;
- log security-relevant success and failure events without logging secret-like payloads.

Expected areas:

- `src/Application/WebAuthn/`;
- `src/Security/WebAuthn/`;
- `src/Infrastructure/Persistence/`;
- `tests/Application/WebAuthn/`;
- `tests/Http/Controller/`.

### Step 7: Authentication Challenge Primitive

Prepare the challenge used later by Password + Passkey login.

Expected behavior:

- generate an authentication challenge for a known user;
- restrict allowed credential ids to that user's active credentials;
- store the challenge with expiration;
- return options for `navigator.credentials.get()`.

Security focus:

- this step prepares v0.9 but does not complete the login flow;
- challenge state must be separate from enrollment challenge state when needed;
- revoked credentials must not be offered.

Expected areas:

- `src/Application/WebAuthn/`;
- `src/Security/WebAuthn/`;
- `tests/Application/WebAuthn/`.

## Out Of Scope

`v0.8.0` should not implement:

- public signup;
- passwordless login;
- replacing TOTP;
- complete Password + Passkey login;
- trusted devices;
- Passkey recovery;
- complex multi-Passkey management UI;
- production attestation policy beyond the documented baseline.

## Initial Code Map

Likely new backend areas:

- `src/Security/WebAuthn/`
  - low-level WebAuthn option building, encoding helpers, and verification boundary;
- `src/Application/WebAuthn/`
  - enrollment and authentication challenge workflows;
- `src/Infrastructure/Persistence/`
  - Passkey credential and challenge persistence;
- `src/Http/Controller/`
  - account-security routes for Passkey enrollment;
- `tests/Security/WebAuthn/`, `tests/Application/WebAuthn/`, and `tests/Http/Controller/`
  - focused unit and integration tests.

Likely frontend areas:

- `resources/js/`
  - focused WebAuthn browser module;
- `tests/frontend/`
  - binary encoding and WebAuthn module tests.

This map may be refined as the implementation teaches us more, but changes should remain small and documented after each sub-step.
