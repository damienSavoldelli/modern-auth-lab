# v0.6.0 Password + TOTP Flow Implementation Notes

This note describes how the `v0.6.0 - Password + TOTP Flow` milestone should be approached.

The goal is to turn the TOTP foundation from `v0.5.0` into an enforced second authentication step after password verification.

## Learning Objective

At the end of this milestone, the project should make these concepts clear:

- why password verification is not the same thing as full authentication when MFA is enabled;
- how a session can move from `password_verified` to `mfa_pending` and then to `fully_authenticated`;
- how the server verifies an authenticator-app code during login;
- why TOTP verification needs rate limiting and generic error messages;
- why replaying a previously accepted TOTP time step must be rejected;
- why stale `pending` TOTP credentials should expire instead of living forever;
- why losing or deleting an authenticator entry requires a separate recovery or reset flow.

## Current Starting Point

`v0.5.0` already provides:

- TOTP secret generation;
- `otpauth://` provisioning URI generation;
- QR code rendering for authenticator apps;
- encrypted TOTP secret persistence;
- pending-to-active enrollment confirmation;
- last accepted time-step storage support.

This means `v0.6.0` does not need to rebuild TOTP primitives. It should focus on login behavior, lifecycle hardening, and security controls around the second factor.

## Target Login Flow

The target flow is:

1. User submits email and password on `/login`.
2. Password is verified with the existing password authenticator.
3. If the user has no active TOTP credential, the current non-MFA login behavior remains valid for now.
4. If the user has an active TOTP credential, the session enters an MFA-pending state.
5. User is redirected to a TOTP challenge page.
6. User submits the six-digit code from the authenticator app.
7. Server verifies the code against the encrypted active TOTP secret.
8. If valid and not replayed, the session becomes fully authenticated.
9. If invalid, the response stays generic and the attempt is rate-limited.

## Recommended Step Order

### Step 1: Session State Transition

Introduce the session state needed to represent a user who has passed password verification but still needs MFA.

Expected behavior:

- password success can create an `mfa_pending` state;
- `mfa_pending` stores enough user identity to continue the flow safely;
- private routes still require `fully_authenticated`;
- session rotation remains explicit around meaningful authentication boundaries.

Security focus:

- avoid treating password verification as full authentication when an active TOTP credential exists;
- avoid losing the user identity between password and TOTP challenge;
- keep session states easy to audit in tests.

#### Step 1.1: Session State Model Documentation

This sub-step is documentation-only. It defines the state model before changing the login controller.

The project intentionally does not use a single `is_logged_in` boolean. MFA requires more precision because a user can be partially authenticated: the password may be correct, but the account should still not be treated as fully authenticated until the second factor succeeds.

Current session states:

| State                 | Meaning                                                                            | May Access `/account`? | Typical Next Step                    |
| --------------------- | ---------------------------------------------------------------------------------- | ---------------------- | ------------------------------------ |
| `anonymous`           | No authentication has been completed.                                              | No                     | Submit the password login form.      |
| `password_verified`   | Password was verified, but no full authentication decision has been completed yet. | No                     | Decide whether MFA is required.      |
| `mfa_pending`         | Password was verified and an active MFA method must still be completed.            | No                     | Show and process the TOTP challenge. |
| `fully_authenticated` | Required authentication steps are complete for the current flow.                   | Yes                    | Access protected routes.             |

Important distinction:

- `password_verified` means "the password was correct";
- `mfa_pending` means "the password was correct, but MFA is still required";
- `fully_authenticated` means "the user has completed all required steps for this flow".

Why this matters:

- a password-only session and a password-plus-TOTP session must not collapse into the same state too early;
- protected routes should check only `fully_authenticated`;
- `mfa_pending` must carry the user identity safely so the server knows which active TOTP credential to verify;
- the challenge page must not ask for the email or password again, because that would complicate the flow and increase account-enumeration risk;
- session rotation remains explicit around authentication boundaries instead of being hidden inside a boolean flag.

Current code map:

- `src/Session/AuthSessionState.php`
  - `AuthSessionState::Anonymous` represents an unauthenticated session.
  - `AuthSessionState::PasswordVerified` represents password verification before a final auth decision.
  - `AuthSessionState::MfaPending` represents a session waiting for MFA completion.
  - `AuthSessionState::FullyAuthenticated` represents a session allowed to access protected routes.
  - `AuthSessionState::isFullyAuthenticated()` keeps protected-route checks focused on the final state.
- `src/Session/AuthSession.php`
  - `AuthSession::markPasswordVerified()` stores the password-only intermediate state.
  - `AuthSession::markMfaPending()` stores the MFA-pending state.
  - `AuthSession::markFullyAuthenticated()` stores the final authenticated state and can carry the user identity.
  - `AuthSession::userId()` and `AuthSession::userEmail()` expose the session user identity when available.

What remains for the following sub-steps:

- ensure `mfa_pending` always carries the user id and email needed by the TOTP challenge;
- adapt password login so active TOTP credentials route to `mfa_pending` instead of `fully_authenticated`;
- ensure `/account` and other private routes reject `mfa_pending`;
- add tests that prove the state transitions cannot accidentally bypass MFA.

Stop after this sub-step and validate the model before changing application behavior.

#### Step 1.2: AuthSession MFA Pending Identity

This sub-step updates the session facade so `mfa_pending` can carry the verified user identity.

Why this is needed:

- after password verification, the server already knows which user is trying to authenticate;
- the future `/login/totp` challenge must verify the TOTP code for that user;
- asking for the email again on the TOTP page would add unnecessary UX friction and create more account-enumeration surface;
- storing only the user id without the email would work technically, but carrying both keeps the session consistent with the current fully authenticated state.

Implementation:

- `AuthSession::markMfaPending()` now accepts optional `userId` and `email` arguments;
- the method stores `auth_state = mfa_pending`;
- when provided, it also stores `auth_user_id` and `auth_user_email`;
- `AuthSession::markFullyAuthenticated()` now reuses the same private identity storage helper.

Security implications:

- `mfa_pending` still does not grant access to protected routes;
- the stored identity is not proof of full authentication;
- protected routes must continue checking `AuthSessionState::FullyAuthenticated`;
- the future TOTP challenge can load the active credential by `user_id` without trusting user-submitted account identifiers.

Code map:

- `src/Session/AuthSession.php`
  - `AuthSession::markMfaPending()` records the MFA-pending state and carries verified identity.
  - `AuthSession::storeUserIdentity()` centralizes session identity writes for partial and full authentication.
- `tests/Session/AuthSessionTest.php`
  - `testTracksMfaPendingStateWithVerifiedUserIdentity()` proves that `mfa_pending` stores `auth_user_id` and `auth_user_email`.

What this does not do yet:

- it does not change the password login controller;
- it does not check whether the user has active TOTP;
- it does not add `/login/totp`;
- it does not complete full authentication after TOTP.

#### Step 1.3: Password Login Routes To MFA When TOTP Is Active

This sub-step changes the password login decision after successful password verification.

Before this step:

- a valid email and password always produced a fully authenticated session;
- the user was redirected directly to `/account`;
- TOTP enrollment existed, but login did not require it yet.

After this step:

- a valid email and password still authenticates the password factor;
- if the user has no active TOTP credential, the current password-only flow remains unchanged;
- if the user has an active TOTP credential, the session moves to `mfa_pending`;
- the verified user id and email are stored in the session;
- the user is redirected to `/login/totp`;
- the session id is rotated before leaving the password step.

Decision table:

| Password Result | Active TOTP? | Session State         | Redirect                      |
| --------------- | ------------ | --------------------- | ----------------------------- |
| Failure         | Not checked  | `anonymous`           | Login form with generic error |
| Success         | No           | `fully_authenticated` | `/account`                    |
| Success         | Yes          | `mfa_pending`         | `/login/totp`                 |

Security implications:

- password success no longer means full authentication for users with active TOTP;
- private routes still require `fully_authenticated`, so `mfa_pending` cannot access `/account`;
- the TOTP challenge will use the session user id instead of trusting a newly submitted email;
- login success is still logged at the password factor level, while future steps will add TOTP-specific events;
- the redirect target exists conceptually, but the `/login/totp` route is implemented in the next step.

Code map:

- `src/Http/Controller/PasswordLoginController.php`
  - receives `UserTotpCredentialRepository`;
  - checks `findActiveByUserId()` after password success;
  - calls `AuthSession::markMfaPending()` and redirects to `/login/totp` when TOTP is active;
  - preserves the existing full login behavior when no active TOTP credential exists.
- `public/index.php`
  - injects `UserTotpCredentialRepository` into `PasswordLoginController`.
- `tests/Http/Controller/PasswordLoginControllerTest.php`
  - keeps the password-only success test;
  - adds `testMarksMfaPendingAndRotatesSessionWhenUserHasActiveTotp()`.

What this does not do yet:

- it does not render `/login/totp`;
- it does not verify a submitted TOTP code;
- it does not add TOTP rate limiting;
- it does not add anti-replay enforcement.

### Step 2: TOTP Challenge Page

Add the minimal HTTP surface for the second factor.

Expected behavior:

- `GET /login/totp` renders a TOTP challenge form;
- `POST /login/totp` validates CSRF;
- the page is accessible only when the session is MFA-pending;
- success redirects to the account page;
- failure returns a generic message.

Security focus:

- CSRF remains required because the challenge modifies authentication state;
- errors must not reveal whether a user has TOTP enabled;
- the form must not expose the TOTP secret or provisioning URI.

#### Step 2.1: TOTP Challenge Page Skeleton

This sub-step adds the first HTTP page for the second factor.

Expected behavior:

- `GET /login/totp` exists;

What this does not do yet:

- it does not add `POST /login/totp`;

#### Step 2.2: TOTP Challenge POST Skeleton

This sub-step adds the POST endpoint for the challenge form without verifying the TOTP code yet.

Why a skeleton first:

- CSRF validation and session authorization are HTTP concerns;

Expected behavior:

Security implications:

### Step 3: TOTP Login Verification

Use the active TOTP credential to verify the submitted code.

Expected behavior:

- decrypt the active TOTP secret only inside the application service that needs it;
- verify the submitted code with the credential parameters stored during enrollment;
- accept only the configured tolerance window;
- update the last accepted time step on success.

Security focus:

- encrypted secrets are not logged or rendered;
- verification uses the stored algorithm, digits, and period;
- implementation remains compatible with future parameter versioning.

#### Step 3.1: TOTP Login Verification Service

This sub-step introduces the application service that verifies a TOTP code during login.

Why this service exists:

- the HTTP controller should not decrypt secrets;
- the HTTP controller should not know how TOTP codes are generated;
- the TOTP primitives should not know about users, repositories, or sessions;
- the application service is the correct orchestration layer between persistence and cryptographic verification.

Flow handled by the service:

1. Receive the user id from the MFA-pending session.
2. Load the active TOTP credential for that user.
3. Return a generic failure if no active credential exists.
4. Decrypt the protected TOTP secret.
5. Recreate the TOTP verifier from the stored credential parameters:
   - algorithm;
   - digits;
   - period.
6. Verify the submitted code against the current accepted time window.
7. Store the accepted time step when verification succeeds.
8. Return a generic success/failure result.

Why the service uses stored parameters:

The authenticator app and the server must calculate the same code from the same inputs:

- shared secret;
- algorithm;
- number of digits;
- time period.

Those values were fixed during enrollment and stored with the credential. Login verification must reuse them instead of assuming global defaults forever. This keeps the system compatible with future parameter migration or versioning.

Security implications:

- the submitted code is never logged;
- the decrypted secret remains inside the verification service boundary;
- failed verification does not reveal whether the user has no active credential or submitted a wrong code;
- the service records the accepted time step for future anti-replay enforcement;
- this step records `last_used_time_step`, but it does not yet reject replayed steps. Effective replay rejection is handled explicitly in Step 4.

Code map:

- `src/Application/Totp/TotpLoginVerificationService.php`
  - `TotpLoginVerificationService::verify()` loads the active credential, decrypts the secret, verifies the submitted code, and records the accepted time step.
- `src/Application/Totp/TotpLoginVerificationResult.php`
  - `TotpLoginVerificationResult::success()` returns a generic successful result with the accepted time step.
  - `TotpLoginVerificationResult::failure()` returns a generic failed result without exposing failure details.
- `tests/Application/Totp/TotpLoginVerificationServiceTest.php`
  - `testVerifiesCodeForActiveTotpCredential()` validates successful verification and time-step recording.
  - `testRejectsCodeWhenNoActiveTotpCredentialExists()` validates generic failure without an active credential.
  - `testRejectsInvalidCodeForActiveTotpCredential()` validates generic failure for an invalid code.

What this does not do yet:

- it does not upgrade the PHP session to `fully_authenticated`;
- it does not replace the temporary `501` response in `TotpChallengeController`;
- it does not reject replayed time steps yet;
- it does not apply TOTP-specific rate limiting.

#### Step 3.2: Wire TOTP Verification Into The Challenge Controller

This sub-step replaces the temporary `501` response from Step 2.2 with real TOTP verification.

HTTP flow after this step:

1. `POST /login/totp` checks that the session is still `mfa_pending`.
2. The controller validates the CSRF token.
3. The controller reads the user id and email from the session.
4. The controller passes only the user id and submitted code to `TotpLoginVerificationService`.
5. If verification fails, the form is re-rendered with a generic error.
6. If verification succeeds, the session becomes `fully_authenticated`.
7. The session id is rotated after successful MFA completion.
8. The user is redirected to `/account`.

Decision table:

| Session State                       | CSRF        | Code        | Result                                                     |
| ----------------------------------- | ----------- | ----------- | ---------------------------------------------------------- |
| `anonymous`                         | Not checked | Not checked | Redirect `/login`                                          |
| `fully_authenticated`               | Not checked | Not checked | Redirect `/account`                                        |
| `mfa_pending` without user id/email | Not checked | Not checked | Redirect `/login`                                          |
| `mfa_pending`                       | Invalid     | Not checked | Generic error                                              |
| `mfa_pending`                       | Valid       | Invalid     | Generic error                                              |
| `mfa_pending`                       | Valid       | Valid       | `fully_authenticated`, rotate session, redirect `/account` |

Security implications:

- the controller never sees or renders the TOTP secret;
- the controller does not ask for the email again;
- both invalid CSRF and invalid TOTP use a generic user-facing error;
- successful MFA is the boundary where the session becomes fully authenticated;
- session rotation after successful MFA reduces fixation risk across the partial-to-full authentication boundary.

Code map:

- `public/index.php`

- `tests/Http/Controller/TotpChallengeControllerTest.php`
  - replaces the temporary `501` test;

- it does not add TOTP success/failure security events.

### Step 4: Anti-Replay Protection

Reject codes from time steps that were already accepted.

Why this matters:

TOTP codes are valid for a short time window. Without replay protection, the same code could be submitted twice during that window. The project already stores `last_used_time_step`; `v0.6.0` should enforce it during login.

Expected behavior:

- if the matched time step is less than or equal to `last_used_time_step`, reject the code;
- if the matched time step is newer, accept it and persist the new value;
- tests should cover current-step success and repeated-step rejection.

#### Step 4.1: Reject Already Accepted TOTP Time Steps

This sub-step turns `last_used_time_step` from tracking metadata into an active security control.

Rule:

```text
A TOTP time step is accepted at most once per credential.
```

Implementation behavior:

1. The submitted code is verified against the normal TOTP tolerance window.
2. If the code does not match any accepted step, verification fails.
3. If the matched step is less than or equal to `last_used_time_step`, verification fails.
4. If the matched step is newer, verification succeeds.
5. The new accepted step is stored as `last_used_time_step`.

Concrete example:

```text
period = 30 seconds
12:00:00 -> 12:00:29
code = 123456
time_step = X
```

Without anti-replay:

```text
12:00:05 -> code 123456 -> accepted
12:00:10 -> same code 123456 -> accepted again
```

With anti-replay:

```text
12:00:05 -> code 123456 -> accepted
server stores last_used_time_step = X

12:00:10 -> same code 123456 -> rejected
```

UX/security tradeoff:

This can reject a legitimate user in a rare case:

```text
12:00:05 -> login succeeds with code 123456
12:00:10 -> user logs out
12:00:15 -> user logs in again with the same code
=> rejected because the time step was already accepted
```

This is acceptable for the project because:

- the scenario is rare;
- the user only needs to wait for the next authenticator code;
- the security gain is meaningful because an accepted MFA proof cannot be reused.

Important detail with `window = 1`:

The verifier may accept:

- previous step;
- current step;
- next step.

Anti-replay therefore rejects not only the exact same code, but any code whose matched step is already used or older. This prevents accepting an older step that still falls inside the clock-drift tolerance window.

Security implications:

- replayed TOTP submissions remain indistinguishable from invalid codes in the UI;
- no user-facing message says "code already used";
- the submitted code is still never logged;
- replay protection is per credential because `last_used_time_step` belongs to the active TOTP credential.

Code map:

- `src/Application/Totp/TotpLoginVerificationService.php`
  - rejects a successful verification result when `timeStep <= lastUsedTimeStep`;
  - records the new time step only after replay checks pass.
- `tests/Application/Totp/TotpLoginVerificationServiceTest.php`
  - `testRejectsAlreadyAcceptedTimeStep()` proves the same step cannot be reused.
  - `testRejectsOlderAcceptedTimeStepInsideVerificationWindow()` proves an older accepted step is rejected even when still inside the tolerance window.

### Step 5: MFA Rate Limiting And Events

Add basic protections around repeated TOTP failures.

Expected behavior:

- rate-limit repeated TOTP challenge failures;
- log success and failure security events;
- keep user-facing errors generic.

Security focus:

- six-digit TOTP codes are small enough to need brute-force controls;
- logs should help explain what happened without storing the submitted code;
- sensitive values must never be logged.

#### Step 5.1: TOTP Rate Limit Configuration

This sub-step adds environment-driven configuration for TOTP challenge rate limiting.

Why configuration comes first:

- rate-limit thresholds are security policy, not hardcoded controller behavior;
- local development, CI, and production may need different values;
- invalid values should fail explicitly instead of silently weakening protection.

Environment variables:

```env
TOTP_RATE_LIMIT_MAX_ATTEMPTS=5
TOTP_RATE_LIMIT_LOCK_SECONDS=300
```

Meaning:

- `TOTP_RATE_LIMIT_MAX_ATTEMPTS=5` allows up to five failed TOTP submissions before the challenge is temporarily blocked.
- `TOTP_RATE_LIMIT_LOCK_SECONDS=300` blocks the challenge for 300 seconds, which is five minutes.

Why these defaults are reasonable for the project:

- six-digit TOTP codes have a small enough search space to need throttling;
- five failed attempts gives normal users room for typing mistakes;
- five minutes is long enough to slow brute force without making local testing painful.

Validation rules:

- both values must exist;
- both values must be integers;
- both values must be greater than zero.

Security implications:

- the configuration controls brute-force resistance for the second factor;
- the submitted TOTP code is never stored in configuration, session, database, or logs;
- `.env.local` carries local runtime values and remains ignored by Git;
- `.env.example` documents required variables without carrying secrets.

Code map:

- `.env.example`
  - documents `TOTP_RATE_LIMIT_MAX_ATTEMPTS`;
  - documents `TOTP_RATE_LIMIT_LOCK_SECONDS`.
- `.env.local`
  - receives local development values for manual testing.
- `src/Security/Totp/TotpRateLimitConfig.php`
  - `TotpRateLimitConfig::fromEnvironment()` loads and validates both values.
- `tests/Security/Totp/TotpRateLimitConfigTest.php`
  - covers valid configuration;
  - covers whitespace trimming;
  - covers missing, non-integer, and zero values.

What this does not do yet:

- it does not block TOTP attempts yet;
- it does not store failed attempt counters yet;
- it does not wire rate limiting into `TotpChallengeController`;
- it does not add security events yet.

#### Step 5.2: TOTP Challenge Rate Limiter

This sub-step adds the actual TOTP challenge rate limiter.

Why it is TOTP-specific:

- password login and TOTP challenge are different attack surfaces;
- password attempts happen before user identity is trusted;
- TOTP attempts happen after password verification, so the system can rate-limit by a key derived from the verified user id and client IP;
- separating the limiters keeps future policies independent.

Storage model:

- the limiter is session-backed for this project stage;
- it stores failed-attempt timestamps;
- it stores `locked_until`;
- it does not store submitted TOTP codes;
- it does not store TOTP secrets;
- it does not know about email, user id, or IP directly.

Identifier responsibility:

`TotpChallengeRateLimiter` accepts an opaque identifier:

```text
totp-key
```

The future controller wiring step will build that key from:

```text
user_id + client IP
```

The limiter deliberately does not build the key itself. This keeps HTTP/request semantics out of the low-level limiter.

Current policy:

```text
maxAttempts = TOTP_RATE_LIMIT_MAX_ATTEMPTS
lockSeconds = TOTP_RATE_LIMIT_LOCK_SECONDS
```

For now, `lockSeconds` is also used as the short observation window for recent failures. With the default values, this means:

```text
5 failed attempts inside roughly 5 minutes
=> lock for 5 minutes
```

This keeps the first implementation simple while still making the policy configurable. If the project later needs more precision, a separate `TOTP_RATE_LIMIT_WINDOW_SECONDS` variable can be introduced.

Security implications:

- repeated invalid codes can be slowed down before brute force becomes practical;
- rate-limit state is scoped to the chosen identifier, not to the raw code;
- session-backed storage is acceptable for this milestone, but a shared store would be needed for multi-server deployments;
- successful MFA should clear the limiter in the next wiring step.

Code map:

- `src/Security/Totp/TotpChallengeRateLimiter.php`
  - `isAllowed()` checks whether the identifier is currently locked;
  - `recordFailure()` stores a failed attempt and locks at the threshold;
  - `clear()` removes limiter state after a successful challenge.
- `tests/Security/Totp/TotpChallengeRateLimiterTest.php`
  - validates attempts before the threshold;
  - validates lock after the threshold;
  - validates unlock after expiration;
  - validates clearing after success;
  - validates old attempts are ignored outside the configured window.

What this does not do yet:

- it does not run inside `TotpChallengeController`;
- it does not choose the final user/IP identifier;
- it does not return HTTP `429` yet;
- it does not log rate-limited events yet.

#### Step 5.3: Wire TOTP Rate Limiter Into The Challenge Controller

This sub-step applies the TOTP challenge rate limiter to `POST /login/totp`.

Runtime behavior:

1. The controller validates session eligibility.
2. The controller validates CSRF.
3. The controller reads the verified user id and email from the MFA-pending session.
4. The controller builds an opaque rate-limit key from:
   - user id;
   - server-observed client IP.
5. If the key is currently blocked, the controller returns HTTP `429`.
6. If the submitted TOTP code is invalid, the controller records a failure.
7. If the submitted TOTP code is valid, the controller clears the limiter.
8. Successful MFA still rotates the session and redirects to `/account`.

Rate-limit identifier:

```text
hash(user_id + "|" + client_ip)
```

Why the identifier is hashed:

- the limiter storage does not need raw IP addresses;
- the key remains deterministic for the same user/IP pair;
- the controller owns request semantics while the limiter receives only an opaque string.

User-facing behavior:

- invalid code returns HTTP `400` with `Invalid authenticator code.`;
- too many attempts returns HTTP `429` with `Too many attempts. Try again later.`;
- successful code returns HTTP `303` to `/account`.

Security implications:

- TOTP brute force is now throttled after password verification;
- failed TOTP attempts are counted only after CSRF succeeds;
- successful TOTP clears previous failures for the same user/IP key;
- no submitted TOTP code is logged or persisted;
- rate limiting is currently session-backed and will need a shared store in distributed deployments.

Code map:

- `src/Http/Controller/TotpChallengeController.php`
  - receives `TotpChallengeRateLimiter`;
  - receives the server-observed client IP;
  - checks `isAllowed()` before verification;
  - calls `recordFailure()` after invalid TOTP;
  - calls `clear()` after successful TOTP.
- `public/index.php`
  - loads `TotpRateLimitConfig` from runtime environment;
  - injects `TotpChallengeRateLimiter`;
  - passes `clientIp()` to the challenge controller.
- `tests/Http/Controller/TotpChallengeControllerTest.php`
  - covers repeated invalid-code lockout;
  - covers limiter clearing after successful challenge.

What this does not do yet:

- it does not add security event logging for TOTP success, failure, or rate limiting;
- it does not move limiter storage out of the PHP session.

### Step 6: Pending Enrollment Expiration

Add lifecycle cleanup for old `pending` TOTP credentials.

Expected behavior:

- define a pending lifetime, recommended initial value: 30 minutes;
- when setup starts, expired pending credentials are revoked and replaced;
- document why the pending secret should not remain usable indefinitely.

Security focus:

- `pending` does not grant authentication, but it still contains a protected secret;
- old pending credentials create unnecessary sensitive data retention;
- revoking instead of silently deleting keeps an auditable lifecycle.

## Future Work After v0.6.0

The following items are intentionally not part of the first TOTP login milestone:

- user-facing TOTP disable flow;
- user-facing TOTP reset/regeneration flow;
- lost-authenticator recovery;
- recovery codes;
- trusted-device based recovery;
- Passkey-backed recovery.

These flows are security-sensitive because they can remove or bypass MFA. They should be designed as explicit lifecycle and recovery work after the core Password + TOTP login flow is understood and tested.
