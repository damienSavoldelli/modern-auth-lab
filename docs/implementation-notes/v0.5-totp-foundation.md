# v0.5.0 TOTP Foundation Implementation Notes

This note describes how the `v0.5.0 - TOTP Foundation` milestone should be approached.

The goal is to build TOTP understanding and core primitives before wiring TOTP into the full login flow.

## Learning Objective

At the end of this milestone, the project should make these concepts clear:

- what a TOTP secret is;
- how an authenticator app receives the secret;
- what `otpauth://` is used for;
- how a time-based code is generated;
- how the server verifies a submitted code;
- why enrollment must be confirmed before activation;
- why TOTP does not provide per-device revocation.

## Where The Work Should Happen

Expected backend areas:

- `src/Security/Totp/` for TOTP primitives such as secrets, URI generation, and verification.
- `tests/Security/Totp/` for focused unit tests.
- `docs/concepts/totp.md` for conceptual explanation updates.
- `docs/decisions/` for ADRs when persistence, encryption, enrollment state, or lifecycle decisions are introduced.

Expected later areas:

- `src/Infrastructure/Persistence/` when TOTP persistence is introduced.
- `src/Http/Controller/` when enrollment screens or actions are introduced.
- `src/Application/` when TOTP enrollment becomes a workflow instead of a primitive.

## Recommended Step Order

### Step 1: TOTP Concepts And Pure Logic

Implement only the pure logic:

- Base32-compatible secret representation.
- TOTP secret generation.
- HOTP/TOTP code calculation.
- TOTP verification with a small time window.
- `otpauth://` URI generation.

Do not add database persistence yet.

Stop after this step and validate understanding.

#### Step 1.1: Base32 Encoding

TOTP secrets are generated as raw random bytes, but authenticator apps commonly receive them as Base32 text inside the `otpauth://` URI.

This step adds:

- `src/Security/Totp/Base32.php`
- `tests/Security/Totp/Base32Test.php`

The Base32 implementation:

- uses the RFC 4648 alphabet: `A-Z` and `2-7`;
- emits unpadded output because TOTP provisioning commonly omits `=`;
- accepts lowercase input during decoding;
- accepts whitespace during decoding;
- accepts but ignores padding during decoding;
- rejects invalid characters explicitly.

Why this step exists:

- TOTP needs Base32 before `otpauth://` URI generation can be correct;
- keeping Base32 isolated makes the encoding rules testable;
- no persistence, session, or HTTP logic is needed to understand this layer;
- using standard PHP keeps the implementation transparent before considering dependencies.

Validation for this step:

- RFC 4648 known vectors;
- empty string behavior;
- lowercase, whitespace, and padding tolerance;
- binary round-trip behavior;
- invalid character rejection.

##### Code Map

Production code:

- `src/Security/Totp/Base32.php`
  - `Base32::encode()` encodes raw bytes into unpadded Base32 text.
  - `Base32::decode()` decodes Base32 text into raw bytes and rejects invalid characters.

Tests:

- `tests/Security/Totp/Base32Test.php`
  - `testEncodesKnownRfc4648VectorsWithoutPadding()` validates known RFC 4648 vectors without `=` padding.
  - `testDecodesKnownRfc4648VectorsWithoutPadding()` validates decoding of known RFC 4648 vectors.
  - `testDecodesLowercaseWhitespaceAndPadding()` validates authenticator-friendly input tolerance.
  - `testRoundTripsBinaryData()` validates binary-safe encode/decode behavior.
  - `testRejectsInvalidCharacters()` validates explicit rejection of invalid Base32 input.

#### Step 1.2: TOTP Secret

This step introduces the TOTP shared secret as a dedicated value object.

Files:

- `src/Security/Totp/TotpSecret.php`
- `tests/Security/Totp/TotpSecretTest.php`

The TOTP secret is security-critical. It is not the six-digit code shown by the authenticator app. It is the long-lived key used to compute those codes.

Rules introduced:

- default generated length: 20 random bytes;
- minimum accepted length: 16 bytes;
- Base32 is used as the provisioning representation;
- raw bytes remain available only for internal verifier code;
- invalid Base32 input is rejected;
- short generated or imported secrets are rejected;
- no `__toString()` method is provided to avoid accidental logging or display.

Why 20 bytes by default:

- 20 bytes equals 160 bits;
- it matches common HOTP/TOTP examples based on HMAC-SHA1;
- it is stronger than short human-entered secrets;
- it remains compatible with authenticator-app provisioning.

Why enforce a minimum:

- TOTP security depends on the shared secret;
- accepting very short secrets would weaken every future generated code;
- enforcing the policy at the value-object boundary keeps later code safer.

Validation for this step:

- generated default length;
- generated custom length;
- Base32 import;
- Base32 normalization;
- rejection of generated secrets below policy;
- rejection of imported secrets below policy;
- rejection of invalid Base32 input.

##### Code Map

Production code:

- `src/Security/Totp/TotpSecret.php`
  - `TotpSecret::generate()` creates a new random shared secret.
  - `TotpSecret::fromBase32()` recreates a secret from a provisioning value.
  - `TotpSecret::base32()` returns the Base32 provisioning representation.
  - `TotpSecret::bytes()` returns raw bytes for future HOTP/TOTP verifier logic.

Tests:

- `tests/Security/Totp/TotpSecretTest.php`
  - `testGeneratesDefaultTwentyByteSecret()` validates the default 20-byte secret policy.
  - `testGeneratesCustomLengthSecret()` validates custom secure secret lengths.
  - `testRecreatesSecretFromBase32()` validates reconstruction from provisioning data.
  - `testNormalizesBase32Input()` validates lowercase, whitespace, and padding tolerance.
  - `testRejectsGeneratedSecretsBelowMinimumLength()` validates generated-secret length policy.
  - `testRejectsImportedSecretsBelowMinimumLength()` validates imported-secret length policy.
  - `testRejectsInvalidBase32Input()` validates propagation of Base32 validation.

#### Step 1.3: `otpauth://` Provisioning URI

This step introduces the URI format consumed by authenticator apps during enrollment.

The URI is not the QR code. It is the text payload that will later be encoded inside a QR code.

Provisioning chain:

```text
TotpSecret
    -> Base32
    -> otpauth:// URI
    -> QR code
    -> authenticator app
```

Default URI parameters:

```text
Type        = TOTP
Service     = Modern Auth Lab
Account     = dev@example.com
Secret      = Base32 shared secret
Algorithm   = SHA1
Digits      = 6
Period      = 30 seconds
```

Files:

- `src/Security/Totp/TotpProvisioningUri.php`
- `tests/Security/Totp/TotpProvisioningUriTest.php`

Rules introduced:

- the URI type is `totp`;
- `issuer` must not be empty;
- `accountLabel` must not be empty;
- the secret is read from `TotpSecret::base32()`;
- URI label and query parameters are RFC 3986 encoded;
- default algorithm is `SHA1`;
- default digits value is `6`;
- default period is `30` seconds;
- supported algorithms are `SHA1`, `SHA256`, and `SHA512`;
- supported digits values are `6` and `8`;
- period must be at least `1` second;
- no `__toString()` method is provided because the URI contains the TOTP secret.

Why `SHA1`, `6`, and `30` by default:

- these defaults are widely compatible with authenticator apps;
- TOTP commonly uses HMAC-SHA1 even though SHA1 is not recommended for new general-purpose signatures;
- the risk model is different from raw SHA1 signatures because TOTP uses HMAC with a shared secret and short time window;
- the class remains configurable so stronger algorithms and longer codes can be tested.

Validation for this step:

- default URI generation;
- configurable URI generation;
- percent-encoding for issuer and account label;
- rejection of empty issuer;
- rejection of empty account label;
- rejection of unsupported algorithms;
- rejection of unsupported digit lengths;
- rejection of invalid periods.

##### Code Map

Production code:

- `src/Security/Totp/TotpProvisioningUri.php`
  - `TotpProvisioningUri::__construct()` validates provisioning parameters.
  - `TotpProvisioningUri::uri()` builds the `otpauth://` URI.

Tests:

- `tests/Security/Totp/TotpProvisioningUriTest.php`
  - `testBuildsDefaultProvisioningUri()` validates the default compatible URI.
  - `testBuildsConfigurableProvisioningUri()` validates configurable algorithm, digits, and period.
  - `testRejectsEmptyIssuer()` validates issuer requirements.
  - `testRejectsEmptyAccountLabel()` validates account label requirements.
  - `testRejectsUnsupportedAlgorithm()` validates algorithm policy.
  - `testRejectsUnsupportedDigits()` validates digit-length policy.
  - `testRejectsInvalidPeriod()` validates period policy.

#### Step 1.4: TOTP Code Generation

This step introduces deterministic TOTP code generation.

The server and the authenticator app generate the same code because both sides know the same enrollment parameters:

- shared secret;
- algorithm;
- digits;
- period;
- current time.

TOTP is based on HOTP:

```text
HOTP = secret + counter
TOTP = secret + floor(timestamp / period)
```

Files:

- `src/Security/Totp/TotpGenerator.php`
- `tests/Security/Totp/TotpGeneratorTest.php`

Rules introduced:

- default algorithm is `SHA1`;
- default digits value is `6`;
- default period is `30` seconds;
- supported algorithms are `SHA1`, `SHA256`, and `SHA512`;
- supported digits values are `6` and `8`;
- period must be at least `1` second;
- timestamp must not be negative;
- generated codes are returned as strings so leading zeroes are preserved.

Why this step exists:

- the server must be able to compute the same code as the authenticator app;
- the code must be deterministic for a given secret, timestamp, and configuration;
- verification should be built on top of generation, not mixed into it immediately.

Validation for this step:

- RFC 6238 vectors for `SHA1`, `SHA256`, and `SHA512`;
- default six-digit code generation;
- configured period behavior;
- rejection of unsupported algorithms;
- rejection of unsupported digit lengths;
- rejection of invalid periods;
- rejection of negative timestamps.

##### Why RFC 6238 Test Vectors Matter

RFC 6238 defines the TOTP algorithm and provides official test vectors.

A test vector is a known input/output example from the standard. For example:

```text
secret    = known shared secret
timestamp = 59
algorithm = SHA1
digits    = 8
expected  = 94287082
```

The project uses these vectors to prove that `TotpGenerator` is compatible with the standard, not merely that it returns a string with the right length.

These vectors validate security-sensitive implementation details:

- time-step calculation with `floor(timestamp / period)`;
- HOTP counter packing as an unsigned 64-bit big-endian integer;
- HMAC calculation;
- dynamic truncation;
- modulo reduction to the requested digit length;
- zero-padding of short numeric results.

This matters because a code that looks like a valid TOTP can still be incompatible with authenticator apps if any of those details are wrong.

References:

- RFC 6238, TOTP: Time-Based One-Time Password Algorithm  
  https://datatracker.ietf.org/doc/html/rfc6238
- RFC 4226, HOTP: An HMAC-Based One-Time Password Algorithm  
  https://datatracker.ietf.org/doc/html/rfc4226

Production code:

  - `TotpGenerator::__construct()` validates generation parameters.
  - `TotpGenerator::generate()` generates the expected code for a secret and timestamp.

Tests:

- `tests/Security/Totp/TotpGeneratorTest.php`
  - `testGeneratesKnownRfc6238Vectors()` validates standard test vectors.
  - `testGeneratesDefaultSixDigitCode()` validates the project default code format.

#### Step 1.5: TOTP Enrollment Parameters Decision

This step is documentation and architecture only.

It records that TOTP configuration is part of a user's enrollment, not just a global application setting.

Why this step exists now:

- `TotpProvisioningUri` sends `algorithm`, `digits`, and `period` to the authenticator app;
- `TotpGenerator` uses the same parameters to generate the expected code;
- changing these parameters later without remembering each user's enrollment configuration can break existing authenticator apps.

Future persistence must store:

- secret;
- algorithm;
- digits;
- period;
- enrollment status;
- confirmation timestamp;
- last used time step;
- replacement or revocation state when lifecycle flows are introduced.

Example risk:

```text
User enrolls with SHA1 / 6 digits / 30 seconds.
Authenticator app stores those parameters.
Server later changes global defaults to SHA512 / 8 digits / 60 seconds.
The app and server now generate different codes.
The user can be locked out.
```

Decision record:

- `docs/decisions/0013-totp-enrollment-parameters.md`

Documentation updated:

- `docs/concepts/totp.md`
- `docs/implementation-notes/v0.5-totp-foundation.md`

### Step 3: TOTP Enrollment

Introduce an authenticated enrollment flow:

- start enrollment;

Stop after this step and validate the user/security flow.

## Explicit Non-Goals For v0.5.0

- Do not require TOTP during login yet.
- Do not replace the full session login flow yet.
- Do not add Passkeys/WebAuthn.
- Do not implement recovery flows.
- Do not implement trusted devices.
- Do not implement SMS or email OTP.
- Do not build a complex frontend experience.

## Documentation Rule

Each implementation step must update documentation when it introduces a concept that matters for security or future article writing.

The explanation should include:

- the problem being solved;
- the security risk;
- the chosen implementation;
- the tradeoffs;
- what remains intentionally deferred.

After each major block, stop and ask whether the explanation is clear before continuing.
