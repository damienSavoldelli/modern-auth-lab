# v0.3.0 User And Password Foundation Implementation Notes

This note reconstructs the `v0.3.0 - User And Password Foundation` milestone from Git history, PRs, changelog, ADRs, and the tagged file tree.

The goal of this milestone was to introduce users, password hashing, password verification, a minimal CSRF-protected login form, and a local development seed user.

## Learning Objective

At the end of this milestone, the project should make these concepts clear:

- how user records are persisted;
- why password hashes are stored instead of passwords;
- why PHP's native password APIs are preferred at this stage;
- how password verification becomes an application workflow;
- why login errors must stay generic;
- why a successful password check is still an authentication state transition, not just a boolean result.

## Step 1: Users Persistence Schema

The milestone first introduced the user table.

Important files:

- `src/Infrastructure/Persistence/Migrations/CreateUsersTable.php`
- `tests/Infrastructure/Persistence/Migrations/CreateUsersTableTest.php`
- `docs/decisions/0008-user-password-foundation.md`

Expected stored data:

- stable user id;
- email address;
- password hash;
- operational timestamps.

Why the table appears before login:

- authentication must verify against persisted user records;
- tests can validate persistence separately from HTTP behavior;
- later MFA credentials need a stable user owner.

Security implication:

- plaintext passwords are never stored;
- the schema prepares for lookup by email without exposing whether an account exists in HTTP responses.

## Step 2: User Domain Model And Repository

The domain and persistence boundary were separated.

Important files:

- `src/Domain/User/User.php`
- `src/Infrastructure/Persistence/UserRepository.php`
- `tests/Infrastructure/Persistence/UserRepositoryTest.php`

Why a repository:

- controllers and application services should not write SQL directly;
- persistence details stay behind one API;
- future changes to SQLite/libSQL behavior can be isolated.

Architecture implication:

- `User` represents application data;
- `UserRepository` owns database access;
- authentication services can depend on user lookup without knowing the schema details.

## Step 3: Password Hashing

Password hashing was implemented with PHP's native password APIs.

Important files:

- `src/Security/Password/PasswordHasher.php`
- `tests/Security/Password/PasswordHasherTest.php`

Why `password_hash()`:

- it is the standard PHP API for password hashing;
- it uses algorithms designed for password storage;
- it can evolve with PHP defaults;
- it avoids designing a custom password hashing scheme.

Why `password_verify()`:

- it verifies hashes using the metadata embedded in the hash;
- it avoids direct string comparison mistakes;
- it keeps the verification API aligned with `password_hash()`.

Security implication:

- passwords are treated as secrets only at the form and verification boundary;
- the database stores a one-way password hash, not the password;
- password policy complexity is intentionally deferred until the project needs registration or password change flows.

## Step 4: Password Authentication Workflow

The password authenticator connected user lookup and password verification.

Important files:

- `src/Application/Auth/PasswordAuthenticator.php`
- `src/Application/Auth/PasswordAuthenticationResult.php`
- `tests/Application/Auth/PasswordAuthenticatorTest.php`

Why an application service:

- authentication is more than a repository lookup;
- it combines user lookup, password verification, and a generic result;
- controllers should not own password security logic.

Security implication:

- failed authentication should not reveal whether the email exists;
- password verification remains centralized;
- later rate limiting and security event logging can wrap this workflow.

## Step 5: Minimal Login Form

The HTTP login form was added after the backend authentication workflow existed.

Important files:

- `src/Http/Controller/PasswordLoginController.php`
- `public/index.php`
- `src/Http/Router.php`
- `src/Http/Response.php`
- `tests/Http/Controller/PasswordLoginControllerTest.php`
- `docs/decisions/0009-password-login-form.md`

Behavior:

- `GET /login` renders a minimal HTML form;
- `POST /login` validates CSRF;
- submitted credentials are passed to `PasswordAuthenticator`;
- success marks the session as `password_verified`;
- success rotates the session id;
- failure returns a generic error.

Why HTML support was added:

- the previous HTTP foundation only needed JSON for `/health`;
- login requires a browser-facing form;
- the project still avoids a SPA because server-side auth boundaries are easier to audit at this stage.

Security implication:

- CSRF validation is applied to login submission;
- session rotation reduces fixation risk after a successful authentication state change;
- failure messages avoid account enumeration.

## Step 6: Development User Seed Command

A local seed command was added so the login flow could be tested manually.

Important files:

- `bin/seed-dev-user.php`
- `src/Application/User/DevUserSeeder.php`
- `src/Application/User/DevUserSeedResult.php`
- `tests/Application/User/DevUserSeederTest.php`

Purpose:

- create a predictable local development user;
- avoid manual SQL edits during demos;
- keep demo setup reproducible.

Security clarification:

- this is a development helper, not production registration;
- the seeded credentials should not be treated as real credentials;
- production account creation, password reset, and email verification are intentionally deferred.

Manual demo credentials introduced by this milestone:

```text
Email: dev@example.com
Password: password123
```
