# v0.9.0 Password + Passkey Flow Implementation Notes

This note describes how the `v0.9.0 - Password + Passkey Flow` milestone should be approached.

The goal is to connect the WebAuthn primitives delivered in `v0.8.0` to a real, wired, testable Password + Passkey login path. Enrollment must become usable from the browser. Authentication must be fully verified server-side.

## Learning Objective

At the end of this milestone, the project should make these concepts clear:

- how Passkey enrollment flows from the browser API call to credential persistence;
- why the server must verify both the enrollment attestation and the login assertion;
- what server-side assertion verification does and why it cannot be skipped;
- how to model a second pending MFA method alongside TOTP without collapsing session states;
- why the pending MFA method must be tracked server-side, not inferred from the browser;
- why Passkey revocation is per-credential, not per-account;
- what security events are relevant for Passkey enrollment, authentication, and revocation;
- how cross-device authentication uses the same server model as platform authenticators.

## Current Starting Point

`v0.8.0` provides:

- WebAuthn relying-party configuration;
- Base64URL encoding helpers;
- Passkey credential persistence (`user_passkey_credentials`);
- WebAuthn challenge persistence (`webauthn_challenges`);
- `PasskeyEnrollmentChallengeService` ready to generate enrollment options;
- `PasskeyEnrollmentVerificationService` ready to verify attestation and store a credential;
- `PasskeyAuthenticationChallengeService` ready to generate authentication options;
- browser modules for Base64URL conversion and future `navigator.credentials.create()`;
- no HTTP routes for any of the above;
- no browser-wired UI.

The login controller currently checks for active TOTP after password verification. It does not yet check for Passkeys. The session model has `MfaPending` but does not track which MFA method is required.

## Product Boundary

This milestone delivers a browser-usable Passkey enrollment and a wired Password + Passkey login path.

Expected entry point for enrollment:

```text
fully authenticated user
  -> /account/security
  -> add Passkey (provide a name)
  -> browser WebAuthn ceremony
  -> server-side attestation verification
  -> Passkey stored and visible on the security page
```

Expected entry point for authentication:

```text
user submits password
  -> password verified
  -> server detects active Passkeys
  -> session marked MfaPending with passkey method
  -> user arrives at Passkey challenge page
  -> browser WebAuthn ceremony
  -> server-side assertion verification
  -> session fully authenticated
```

## Pending MFA Method Decision

`AuthSession` currently models `MfaPending` as a single state shared by TOTP and future Passkey flows. A user with both TOTP and Passkeys active needs the server to track which method the current login attempt should use.

The project will add a `pending_mfa_method` session key alongside the existing `auth_state` key.

Method preference rule for `v0.9.0`:

```text
active Passkeys present  ->  Passkey flow  (TOTP fallback deferred to v0.10)
TOTP active, no Passkeys ->  TOTP flow     (existing behavior unchanged)
neither                  ->  FullyAuthenticated (existing behavior unchanged)
```

The fallback path from Passkey to TOTP is explicitly deferred to `v0.10.0 - Secure Fallback Strategy`.

## Recommended Step Order

### Step 1: Session MFA Method Tracking

Extend `AuthSession` to track which MFA method is pending for the current login attempt.

Expected behavior:

- `markMfaPending()` gains an optional `pendingMethod` parameter;
- `pendingMfaMethod()` returns the stored method value or null;
- the stored value is a plain string enum: `'totp'` or `'passkey'`;
- existing TOTP flow remains unchanged.

Security focus:

- the pending method must be stored server-side in the session, not sent from the browser;
- the Passkey challenge controller must verify the session carries `passkey` as the pending method before accepting any WebAuthn response.

Expected areas:

- `src/Session/AuthSession.php`;
- `src/Session/PendingMfaMethod.php` (new string-backed enum);
- `tests/Session/`.

#### Step 1.1: PendingMfaMethod Enum And AuthSession Extension

Add `PendingMfaMethod` with `Totp` and `Passkey` cases. Extend `AuthSession` with:

- a new `AUTH_PENDING_MFA_METHOD_KEY` session constant;
- an updated `markMfaPending()` accepting an optional `PendingMfaMethod`;
- a `pendingMfaMethod()` reader.

Code map:

- `src/Session/PendingMfaMethod.php`
  - string-backed enum: `Totp = 'totp'`, `Passkey = 'passkey'`.
- `src/Session/AuthSession.php`
  - adds `AUTH_PENDING_MFA_METHOD_KEY`;
  - extends `markMfaPending()`;
  - adds `pendingMfaMethod()`.
- `tests/Session/AuthSessionTest.php`
  - validates new method tracking alongside existing state behavior.

What remains after Step 1:

- update `PasswordLoginController` to pass the pending method when redirecting to a Passkey flow;
- add Passkey challenge controller that checks the pending method before accepting input.

### Step 2: HTTP Passkey Enrollment Routes

Wire the `v0.8.0` enrollment services to HTTP endpoints behind a fully authenticated session guard.

Expected behavior:

- `POST /account/security/passkeys/enroll/challenge`
  - requires `FullyAuthenticated` session;
  - calls `PasskeyEnrollmentChallengeService`;
  - returns JSON with `publicKey` creation options.
- `POST /account/security/passkeys/enroll/verify`
  - requires `FullyAuthenticated` session;
  - accepts JSON body with the serialized browser credential;
  - accepts a user-provided Passkey name;
  - calls `PasskeyEnrollmentVerificationService`;
  - returns JSON success or failure.

Security focus:

- both routes require a fully authenticated session, not `MfaPending`;
- the JSON body from the browser is untrusted until verified;
- failed verification must return a generic error without exposing protocol details;
- security events must be recorded for enrollment success and failure.

Expected areas:

- `src/Http/Controller/PasskeyEnrollmentController.php`;
- `public/index.php`;
- `tests/Http/Controller/PasskeyEnrollmentControllerTest.php`.

#### Step 2.1: Challenge Route

Add `POST /account/security/passkeys/enroll/challenge`.

Code map:

- `src/Http/Controller/PasskeyEnrollmentController.php`

- `public/index.php`
  - register route.

#### Step 2.2: Attestation Verification Route

Add `POST /account/security/passkeys/enroll/verify`.

The route reads a JSON body. It extracts:

- `credential`: the serialized browser credential object;
- `name`: user-provided label for the new Passkey.

Code map:

- `src/Http/Controller/PasskeyEnrollmentController.php`

#### Step 2.3: Controller Tests

Tests must cover:

### Step 4: Server-Side Assertion Verification

Add the server-side WebAuthn assertion verification boundary needed for Passkey login.

Expected behavior:

- verify challenge against stored unexpired challenge;
- verify origin against `WebAuthnConfig` allowed origins;
- verify RP ID hash;
- verify credential id belongs to the expected user;
- verify signature against stored public key;
- require user presence;
- apply user verification policy;
- evaluate sign counter when available;
- update `last_used_at` on success;
- consume the challenge after success.

Security focus:

- the assertion response is browser-produced and completely untrusted before verification;
- a missing or mismatched challenge is a hard failure;
- a credential belonging to a different user is a hard failure;
- a degraded sign counter is logged but does not fail the assertion by default for synced credentials;
- the verified user id must come from the stored credential, not from browser-provided data.

Expected areas:

- `src/Security/WebAuthn/PasskeyAssertionVerifier.php`;
- `src/Security/WebAuthn/WebAuthnLibPasskeyAssertionVerifier.php`;
- `src/Security/WebAuthn/VerifiedPasskeyAssertion.php`;
- `src/Application/WebAuthn/PasskeyAuthenticationVerificationService.php`;
- `src/Application/WebAuthn/PasskeyAuthenticationVerificationResult.php`;
- `tests/Security/WebAuthn/`;
- `tests/Application/WebAuthn/`.

#### Step 4.1: Verifier Interface And DTO

Define the project-owned assertion verification contract.

Code map:

- `src/Security/WebAuthn/VerifiedPasskeyAssertion.php`
  - carries verified credential id, user id, and updated sign count.
- `src/Security/WebAuthn/PasskeyAssertionVerifier.php`
  - interface: `verify(array $assertionResponse, string $expectedChallenge, UserPasskeyCredential $credential): VerifiedPasskeyAssertion`.

#### Step 4.2: Library Adapter

Adapt `web-auth/webauthn-lib` for assertion verification.

Code map:

- `src/Security/WebAuthn/WebAuthnLibPasskeyAssertionVerifier.php`
  - decodes browser assertion payload;
  - rebuilds expected WebAuthn request options;
  - verifies challenge, origin, RP ID hash, user presence, user verification, signature, and sign counter through the library ceremony.
- `tests/Security/WebAuthn/WebAuthnLibPasskeyAssertionVerifierTest.php`
  - verifies that invalid payloads and mismatched challenges fail at the boundary.

#### Step 4.3: Application Verification Service

Add the application workflow that coordinates challenge, credential, and verifier.

Code map:

- `src/Application/WebAuthn/PasskeyAuthenticationVerificationService.php`
  - loads and checks the challenge;
  - loads the credential by id;
  - verifies the credential belongs to the expected user;
  - calls the assertion verifier;
  - updates `last_used_at`;
  - consumes the challenge.
- `src/Application/WebAuthn/PasskeyAuthenticationVerificationResult.php`
  - carries the verified user id and credential.
- `tests/Application/WebAuthn/PasskeyAuthenticationVerificationServiceTest.php`
  - validates workflow with a fake verifier, covering success, expired challenge, wrong user, and verifier failure cases.

What remains after Step 4:

- browser module for `navigator.credentials.get()`;
- login routes and controller to wire the service to HTTP.

### Step 6: Password + Passkey Login Flow

Wire password verification, MFA method routing, the Passkey challenge page, and the assertion verification service into a complete login path.

Expected behavior:

```text
POST /login
  password verified
  user has active Passkeys
    -> markMfaPending($userId, $email, PendingMfaMethod::Passkey)
    -> generate authentication challenge
    -> redirect to GET /login/passkey

GET /login/passkey
  session must be MfaPending + Passkey method
  render Passkey challenge page
  browser calls navigator.credentials.get()

POST /login/passkey/verify
  session must be MfaPending + Passkey method
  verify assertion
  markFullyAuthenticated()
  rotate session id
  redirect to /account
```

Security focus:

- the Passkey challenge page must refuse non-MfaPending sessions or sessions with the wrong pending method;
- the verified user id must come from the stored credential, not from browser-provided data or session storage alone;
- session rotation is required after full authentication;
- security events must be recorded for Passkey authentication success and failure.

Expected areas:

- `src/Http/Controller/PasswordLoginController.php`;
- `src/Http/Controller/PasskeyLoginController.php`;
- `assets/js/webauthn/passkey-login-ui.js`;
- `public/index.php`;
- `tests/Http/Controller/PasskeyLoginControllerTest.php`.

#### Step 6.1: PasswordLoginController Update

Extend the post-password-verification routing logic.

Current logic:

```text
TOTP active -> markMfaPending -> redirect /login/totp
neither     -> markFullyAuthenticated -> redirect /account
```

Updated logic:

```text
Passkeys active -> markMfaPending(Passkey) -> generate authentication challenge -> redirect /login/passkey
TOTP active, no Passkeys -> markMfaPending(Totp) -> redirect /login/totp (unchanged)
neither -> markFullyAuthenticated -> redirect /account (unchanged)
```

Code map:

  - extend `submit()` to check active Passkeys before TOTP.

#### Step 6.2: Passkey Challenge Controller

### Step 7: Passkey Lifecycle Management

Add individual Passkey revocation accessible from the account security page.

Expected behavior:

- enrolled Passkeys are listed on `/account/security` with name, last used date, and a revoke button;
- `POST /account/security/passkeys/{credentialId}/revoke` revokes one credential;
- only a fully authenticated session may revoke;
- revoked credentials remain stored with `status = revoked` and a `revoked_at` timestamp;
- a security event is recorded on revocation.

Security focus:

- the credential id from the URL must be verified as belonging to the authenticated user before revocation;
- revocation disables future authentication with that credential;
- revoked credentials must not appear in `allowCredentials` during authentication challenges (already enforced by `PasskeyAuthenticationChallengeService`);
- the route must be CSRF-protected because it is a mutation on a sensitive resource.

Expected areas:

- `src/Http/Controller/AccountSecurityController.php`;
- `src/Application/WebAuthn/PasskeyRevocationService.php`;
- `public/index.php`;
- `tests/Application/WebAuthn/PasskeyRevocationServiceTest.php`.

#### Step 7.1: Revocation Service

Code map:

- `src/Application/WebAuthn/PasskeyRevocationService.php`
  - loads the credential by id;
  - verifies it belongs to the requesting user;
  - calls `UserPasskeyCredentialRepository::revoke()`.

#### Step 7.2: Revocation Route

Code map:

- `src/Http/Controller/AccountSecurityController.php`
  - adds `revokePasskey()` method: guard, CSRF, service call, event, redirect.
- `src/Domain/Security/SecurityEventType.php`
  - adds `PasskeyRevoked`.
- `public/index.php`
  - registers `POST /account/security/passkeys/{credentialId}/revoke`.

Note on route parameter: the router is currently path-exact and does not support dynamic segments. If `{credentialId}` requires a pattern-matching router, a minimal path-segment extraction may be needed, or the credential id can be submitted as a POST field instead of a path segment. This decision will be taken during implementation.

What remains after Step 7:

- The full `v0.9.0` scope is complete. Fallback from Passkey to TOTP is deferred to `v0.10.0`.

## Out Of Scope

`v0.9.0` must not implement:

- TOTP fallback when Passkey authentication fails or is unavailable;
- fallback eligibility rules;
- trusted devices;
- recovery-code submission during login;
- cross-device authentication as an explicit separate flow (it is handled by the browser WebAuthn API and uses the same server verification path);
- mandatory MFA policy;
- multiple Passkey enrollment in a single session without page reload.

## Security Events Summary

| Event                            | When                                        | Step   |
| -------------------------------- | ------------------------------------------- | ------ |
| `PasskeyEnrollmentSucceeded`     | Attestation verified and credential stored  | Step 2 |
| `PasskeyEnrollmentFailed`        | Attestation verification fails at any point | Step 2 |
| `PasskeyAuthenticationSucceeded` | Assertion verified and session promoted     | Step 6 |
| `PasskeyAuthenticationFailed`    | Assertion verification fails at any point   | Step 6 |
| `PasskeyRevoked`                 | Credential successfully revoked             | Step 7 |
