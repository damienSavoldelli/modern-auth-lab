# v0.2.0 Session, CSRF And SQLite Foundation Implementation Notes

This note reconstructs the `v0.2.0 - Session, CSRF And SQLite Foundation` milestone from the Git history, changelog, ADRs, and tagged file tree.

The goal of this milestone was to add the first backend security foundations before creating users or login behavior.

## Learning Objective

At the end of this milestone, the project should make these concepts clear:

- why sessions need explicit security defaults;
- why authentication state should not be a simple boolean;
- how CSRF tokens protect unsafe form submissions;
- why SQLite persistence is introduced before user authentication;
- how migrations make database state reproducible;
- why local database files belong under `var/data/`.

## Step 1: Session Foundation

The session foundation introduced a small session abstraction before any user login existed.

Important files:

- `src/Session/NativeSession.php`
- `src/Session/SessionCookieOptions.php`
- `src/Session/AuthSession.php`
- `src/Session/AuthSessionState.php`
- `tests/Session/SessionCookieOptionsTest.php`
- `tests/Session/AuthSessionTest.php`
- `docs/decisions/0005-session-strategy.md`

Why session work comes before login:

- login needs a secure place to store authentication state;
- MFA later requires partial authentication states;
- session rotation must be available before privilege changes are introduced.

Session cookie policy:

- `HttpOnly` reduces exposure to JavaScript access;
- `SameSite=Lax` gives a practical CSRF baseline for normal navigation flows;
- `Secure` is expected for HTTPS environments;
- explicit defaults make security posture visible instead of relying on PHP defaults.

Authentication state model:

- `anonymous` means no authentication has happened;
- `password_verified` means the password factor was accepted but the final flow may not be complete;
- `mfa_pending` prepares the future MFA challenge state;
- `fully_authenticated` means protected routes may be accessed.

Security implication:

- partial authentication is represented explicitly;
- future MFA work can avoid treating a valid password as full authentication.

Architecture implication:

- session handling is not hidden in controllers;
- `AuthSession` becomes the focused boundary for authentication state.

## Step 2: CSRF Token Foundation

The CSRF foundation introduced token generation and validation before unsafe forms existed.

Important files:

- `src/Security/Csrf/CsrfToken.php`
- `src/Security/Csrf/CsrfTokenManager.php`
- `src/Security/Csrf/CsrfTokenException.php`
- `tests/Security/Csrf/CsrfTokenManagerTest.php`
- `docs/decisions/0006-csrf-strategy.md`

Why CSRF exists:

- browsers automatically attach cookies to requests;
- if an unsafe endpoint trusts cookies alone, another site may trigger state-changing actions;
- CSRF tokens bind the form submission to server-side session state.

Why three classes:

- `CsrfToken` represents the token value;
- `CsrfTokenManager` owns generation, storage, and verification;
- `CsrfTokenException` gives explicit failure behavior for invalid submissions.

Security implication:

- invalid CSRF tokens fail closed;
- future login, logout, setup, and recovery forms can share one validation boundary.

Design tradeoff:

- no Composer CSRF package was added;
- the primitive is small enough to keep transparent at this stage;
- a package could be justified later if requirements become broader.

## Step 3: SQLite Persistence Foundation

The persistence foundation introduced local database infrastructure without user data yet.

Important files:

- `src/Infrastructure/Persistence/DatabaseConfig.php`
- `src/Infrastructure/Persistence/SqliteConnectionFactory.php`
- `src/Infrastructure/Persistence/Migration.php`
- `src/Infrastructure/Persistence/MigrationRunner.php`
- `src/Infrastructure/Persistence/MigrationRepository.php`
- `src/Infrastructure/Persistence/Migrations/CreateSchemaMigrationsTable.php`
- `tests/Infrastructure/Persistence/DatabaseConfigTest.php`
- `tests/Infrastructure/Persistence/SqliteConnectionFactoryTest.php`
- `tests/Infrastructure/Persistence/MigrationRunnerTest.php`
- `docs/decisions/0007-sqlite-persistence.md`

Why SQLite first:

- it gives real persistence without requiring a database server;
- it keeps local demos simple;
- it prepares the repository pattern before authentication data is introduced.

Why `var/data/`:

- `var/` is commonly used for runtime-generated project data;
- SQLite database files are runtime state, not source code;
- keeping them outside `public/` prevents accidental web exposure;
- `.gitkeep` preserves the directory shape without committing database files.

Why PDO:

- PDO is part of PHP's standard database ecosystem;
- it avoids adding a dependency before the persistence needs are complex;
- it leaves room for future libSQL investigation without coupling the domain to a specific driver.

Migration model:

- `Migration` describes an executable schema change;
- `MigrationRunner` applies migrations in order;
- `MigrationRepository` tracks applied migrations in `schema_migrations`;
- `CreateSchemaMigrationsTable` bootstraps migration tracking.

Security implication:

- reproducible migrations reduce drift between local, test, and future deployment databases;
- authentication tables can later be added with explicit constraints and indexes.
