# v0.7.0 TOTP Lifecycle And Recovery Implementation Notes

This note describes how the `v0.7.0 - TOTP Lifecycle And Recovery` milestone should be approached.

The goal is to move from "TOTP can be enrolled and required at login" to "TOTP can be managed safely over time".

## Learning Objective

At the end of this milestone, the project should make these concepts clear:

- why an authenticator app cannot notify the server when a user deletes an entry locally;
- why TOTP disable and TOTP recovery are different flows;
- why normal disable should require proof that the user still controls the current TOTP method;
- why lost-authenticator recovery needs stricter controls than normal disable;
- why lifecycle actions must be logged as security events;
- why pending enrollments should not remain valid forever;
- how the project separates account security UI, application workflow, persistence, and security policy.

## Current Starting Point

`v0.5.0` provides:

- TOTP secret generation;
- `otpauth://` provisioning URI generation;
- QR code enrollment;
- encrypted TOTP secret storage;
- pending-to-active enrollment confirmation.

`v0.6.0` provides:

- Password + TOTP login;
- `mfa_pending` session state;
- TOTP challenge verification;
- anti-replay through `last_used_time_step`;
- TOTP challenge rate limiting;
- TOTP login security events;
- pending enrollment expiration and revocation behavior.

This means `v0.7.0` should not rebuild TOTP enrollment or login. It should focus on lifecycle management and recovery preparation.

## Important Product Constraint

Authenticator apps such as Google Authenticator, Aegis, 1Password, or Bitwarden do not call the server when a user deletes a TOTP entry locally.

The server only knows:

- whether it has an active TOTP credential for the user;
- whether submitted TOTP codes verify;
- when the credential was last used successfully;
- whether the user explicitly disabled, reset, or replaced TOTP through the application.

The server does not know:

- whether the authenticator entry still exists on the phone;
- whether the phone was lost;
- whether the user copied the same secret to another device;
- whether the user deleted the entry by mistake.

Security implication:

- local deletion from the authenticator app does not disable server-side MFA;
- the next login still requires TOTP;
- if the user no longer has the code, a recovery flow is required.

## Target User Flows

### Flow A: View TOTP Status

The authenticated user can open an account security page and see whether TOTP is active.

Expected behavior:

- show whether TOTP is enabled;
- show useful lifecycle metadata when available;
- do not show the secret, QR code, provisioning URI, or encrypted payload;
- provide actions only when the current session is allowed to perform them.

### Flow B: Disable TOTP With Current Authenticator

The user still has access to their authenticator app and wants to disable TOTP.

Expected behavior:

- require a fully authenticated session;
- require recent authentication or a fresh TOTP confirmation;
- require the current TOTP code;
- revoke the active TOTP credential;
- log a security event;
- notify the user in the UI.

Security model:

- this is the normal low-friction path because the user can prove possession of the active second factor;
- the server should not disable TOTP based on password alone once TOTP is active.

### Flow C: Lost Authenticator Recovery

The user lost the authenticator or deleted the entry and cannot provide a current TOTP code.

Expected behavior:

- do not silently bypass MFA;
- require a separate recovery mechanism;
- log recovery start, failure, and success events;
- use stricter checks than normal disable;
- leave room for recovery codes, trusted devices, delay, notification, or manual review in later steps.

Security model:

- recovery is a controlled exception path;
- it is higher risk than normal disable because the user cannot prove possession of the current authenticator;
- this flow must be auditable and intentionally scoped.

#### Step 1.1: Read-Only TOTP Security Overview

This sub-step creates the page where future TOTP lifecycle actions will live.

The page is intentionally read-only. It does not disable TOTP, reset TOTP, create recovery codes, or change any credential state.

Expected behavior:

- `GET /account/security` exists;
- anonymous and partial sessions are redirected to `/login`;
- fully authenticated sessions without a stored user id are redirected to `/login`;
- fully authenticated users can see whether TOTP is enabled;
- active TOTP metadata can be displayed when it is safe;
- secret material is never rendered.

Safe data to display:

- status: enabled or disabled;
- algorithm;
- digits;
- period;
- confirmation timestamp;
- last accepted TOTP time step.

Forbidden data on this page:

- raw TOTP secret;
- encrypted TOTP secret payload;
- secret nonce;
- encryption key id;
- `otpauth://` provisioning URI;
- QR code.

Why this step comes first:

- users need a stable account-security location before destructive actions exist;
- the project needs a place to explain lifecycle state without immediately adding recovery complexity;
- read-only status is safer to test and review than disable/reset flows;
- future actions can be added to this page one by one.

Security implications:

- the page requires `fully_authenticated`;
- `mfa_pending` is not enough to access account security settings;
- the server reads TOTP status from persistence instead of trusting frontend state;
- the page exposes lifecycle metadata only, not credential material.

Code map:

- `src/Http/Controller/AccountSecurityController.php`
  - `AccountSecurityController::show()` protects access and loads the active TOTP credential for the authenticated user.
  - `AccountSecurityController::renderPage()` renders the read-only security overview.
  - `AccountSecurityController::renderActiveTotpDetails()` renders safe active credential metadata.
- `public/index.php`
  - registers `GET /account/security`;
  - injects `UserTotpCredentialRepository`.
- `src/Http/Controller/AccountController.php`
  - adds a link to the account security page.
- `tests/Http/Controller/AccountSecurityControllerTest.php`
  - validates redirects for unauthenticated or identity-less sessions;
  - validates disabled TOTP status;
  - validates active TOTP status;
  - validates that secret material is not rendered.

#### Step 2.2: Disable Workflow

This sub-step makes the normal TOTP disable form functional.

Expected behavior:

- `POST /account/security/totp/disable` exists;
- the session must be `fully_authenticated`;
- the session must carry a user id and email;
- CSRF validation is required;
- the submitted authenticator code must verify against the active TOTP credential;
- anti-replay remains enforced through `last_used_time_step`;
- a valid code revokes the active TOTP credential;
- success redirects back to `/account/security`;
- failures return a generic error;
- disable success and disable failure are logged as security events.

Why the current TOTP code is required:

- disabling MFA weakens account protection;
- password-only proof is not enough once TOTP is active;
- requiring the current code proves the user still controls the enrolled authenticator;
- users who cannot provide a code need the stricter recovery flow instead.

Security event policy:

- `totp_disable_succeeded` is recorded after a credential is revoked;
- `totp_disable_failed` is recorded for invalid CSRF or invalid TOTP code;
- submitted TOTP codes are never logged;
- secret ciphertext, nonce, key id, QR code, and provisioning URI are never logged.

Architecture notes:

- `AccountSecurityController` owns HTTP concerns: session eligibility, CSRF, response rendering, and event orchestration.
- `TotpDisableService` owns the application workflow: load active credential, reveal the protected secret, verify the code, enforce anti-replay, and revoke.
- `UserTotpCredentialRepository` remains the persistence boundary.
- `TotpVerifier` and `TotpGenerator` remain the pure TOTP verification boundary.

Code map:

- `src/Application/Totp/TotpDisableService.php`
  - `TotpDisableService::disable()` verifies possession and revokes the active credential.
- `src/Http/Controller/AccountSecurityController.php`
  - `AccountSecurityController::disableTotp()` handles the POST request.
- `src/Domain/Security/SecurityEventType.php`
  - adds `TotpDisableSucceeded`;
  - adds `TotpDisableFailed`.
- `public/index.php`
  - registers `POST /account/security/totp/disable`;
  - wires TOTP secret protection and security event logging.
- `tests/Application/Totp/TotpDisableServiceTest.php`
  - validates successful disable;
  - validates invalid code rejection;
  - validates replayed time-step rejection.
- `tests/Http/Controller/AccountSecurityControllerTest.php`
  - validates invalid CSRF handling;
  - validates invalid code handling;
  - validates successful revocation;
  - validates security event recording without logging submitted codes.

### Step 3: Recovery Strategy Foundation

Define the first recovery model for users who cannot produce a TOTP code.

Expected behavior:

- document the recovery risk model;
- decide whether this milestone introduces recovery codes or only prepares the recovery state;
- define security events for recovery attempts;
- avoid implementing a weak password-only reset.

Security focus:

- recovery must not become an unprotected MFA bypass;
- recovery behavior should be stricter than normal disable;
- future trusted-device and Passkey work must be considered.

#### Step 3.1: Recovery Risk Model And ADR

This sub-step defines the recovery strategy before implementing storage or HTTP behavior.

The key distinction:

```text
Normal disable = user still has the authenticator app
Recovery       = user cannot provide a current TOTP code
```

Normal disable can be low-friction because the user proves possession of the current second factor.

Recovery is higher risk because the user cannot prove possession of the current second factor. If recovery accepts only the password, MFA stops being meaningful against password compromise.

Decision for this project:

- use recovery codes as the first self-service lost-authenticator recovery mechanism;
- generate recovery codes server-side;
- show recovery codes only once;
- store only hashes of recovery codes;
- make recovery codes single-use;
- log recovery events;
- rate-limit recovery submissions;
- defer email, SMS, trusted-device, and admin-assisted recovery.

Why recovery codes:

- they are understandable in a local lab;
- they do not require email or SMS infrastructure;
- they can be stored with password-like one-way hashing;
- they are compatible with future Passkeys and trusted-device work;
- they make the recovery tradeoff explicit instead of hiding it behind password-only reset.

Security implications:

- recovery codes are security-critical credentials;
- raw codes must never be logged or stored;
- users must receive them before losing the authenticator;
- if no recovery method exists, the system should fail closed;
- recovery must stay auditable and separate from normal TOTP disable.

Code map:

- `docs/decisions/0018-totp-recovery-strategy.md`
  - records the accepted recovery strategy and rejected alternatives.
- `docs/concepts/totp.md`
  - explains normal disable vs lost-authenticator recovery.
- `docs/fallback-strategy.md`
  - clarifies that TOTP recovery is not the same as future Passkey fallback.

What this does not implement yet:

- recovery code database schema;
- recovery code generation;
- recovery code display;
- recovery code verification;
- TOTP reset through recovery code.

#### Step 3.2: Recovery Code Persistence Foundation

This sub-step creates persistence for future TOTP recovery codes.

The implementation still does not generate or display recovery codes. It only defines how recovery-code records will be stored safely.

Expected behavior:

- create `user_totp_recovery_codes`;
- attach each recovery code to a user;
- store only `code_hash`, never the raw recovery code;
- track lifecycle status: `active`, `used`, or `revoked`;
- track `used_at` and `revoked_at`;
- allow multiple active recovery codes per user;
- reject duplicate hashes;
- delete recovery-code rows when the user is deleted.

Why a separate table:

- a user can have multiple recovery codes;
- each recovery code has its own lifecycle;
- recovery codes are not TOTP credentials and should not be mixed with `user_totp_credentials`;
- future recovery-code rotation can revoke active codes without touching the active TOTP credential directly.

Security implications:

- raw recovery codes must never be stored;
- `code_hash` is still security-sensitive because it represents a credential verifier;
- codes must become single-use when the verification workflow is implemented;
- recovery-code submission must later be rate-limited and logged;
- recovery codes should be displayed only once when generated.

Code map:

- `src/Infrastructure/Persistence/Migrations/CreateUserTotpRecoveryCodesTable.php`
  - creates `user_totp_recovery_codes`;
  - adds lifecycle status constraints;
  - adds lookup indexes;
  - enforces unique recovery-code hashes.
- `src/Infrastructure/Persistence/UserTotpRecoveryCode.php`
  - represents a recovery-code persistence row without raw code material.
- `src/Infrastructure/Persistence/UserTotpRecoveryCodeRepository.php`
  - `createActive()` stores a hash;
  - `findActiveByUserId()` loads active records;
  - `markUsed()` consumes one active record;
  - `revokeActiveByUserId()` revokes all active records for a user.
- `public/index.php`
  - registers the migration in application startup.
- `tests/Infrastructure/Persistence/Migrations/CreateUserTotpRecoveryCodesTableTest.php`
  - validates schema, foreign key, status constraint, and duplicate-hash rejection.
- `tests/Infrastructure/Persistence/UserTotpRecoveryCodeRepositoryTest.php`
  - validates create, list, use, revoke, and empty-list behavior.

What this does not implement yet:

- recovery-code generation;
- password-style hashing policy for recovery codes;
- one-time display to the user;
- recovery-code verification during account recovery;
- TOTP reset after recovery.

#### Step 3.3: Recovery Code Generation And Hashing

This sub-step adds the recovery-code generation and hashing primitives.

Recovery codes are backup credentials. The user receives the plain code, but the database must store only a verifier.

Expected behavior:

- generate human-readable recovery codes;
- avoid visually confusing characters such as `I`, `O`, `0`, and `1`;
- format codes in groups for easier reading;
- generate a configurable number of codes;
- hash recovery codes before persistence;
- normalize submitted codes before hashing or verification;
- revoke the previous active recovery-code set when a new set is generated;
- return plain codes only to the caller so a future UI can display them once.

Why password-style hashing:

- the server does not need to recover the original recovery code;
- the server only needs to verify a submitted code against a stored verifier;
- one-way hashing reduces impact if SQLite leaks;
- this is different from TOTP secrets, which require reversible encryption because the server must recompute time-based codes.

Security implications:

- recovery codes are security-critical;
- raw recovery codes must not be logged;
- raw recovery codes must not be stored in SQLite;
- a generated set must be shown once and then considered unavailable in plain form;
- replacing a set revokes previously active codes to avoid multiple uncontrolled backup sets.

Code map:

- `src/Security/Totp/TotpRecoveryCodeGenerator.php`
  - `TotpRecoveryCodeGenerator::generate()` creates one readable code.
  - `TotpRecoveryCodeGenerator::generateMany()` creates a unique list.
- `src/Security/Totp/TotpRecoveryCodeHasher.php`
  - `TotpRecoveryCodeHasher::hash()` stores a one-way verifier.
  - `TotpRecoveryCodeHasher::verify()` validates a submitted code.
- `src/Application/Totp/TotpRecoveryCodeService.php`
  - `TotpRecoveryCodeService::generateForUser()` revokes the previous set, generates a new set, and stores hashes.
- `src/Application/Totp/TotpRecoveryCodeGenerationResult.php`
  - carries plain one-time display codes and stored records.
- `tests/Security/Totp/TotpRecoveryCodeGeneratorTest.php`
  - validates format, uniqueness, and constructor rules.
- `tests/Security/Totp/TotpRecoveryCodeHasherTest.php`
  - validates hashing, verification, and input normalization.
- `tests/Application/Totp/TotpRecoveryCodeServiceTest.php`
  - validates hash-only storage and previous-set revocation.

What this does not implement yet:

- account security UI for showing generated recovery codes;
- confirmation that the user saved the codes;
- recovery-code submission during login recovery;
- consuming a recovery code;
- resetting or disabling TOTP through recovery.

#### Step 3.4: Recovery Code Generation UI

This sub-step adds a protected account-security action that generates and displays a recovery-code set.

Expected behavior:

- active TOTP users see a recovery-code generation form on `/account/security`;
- the form submits to `POST /account/security/totp/recovery-codes/generate`;
- CSRF validation is required;
- the user must submit a current TOTP code;
- invalid CSRF or invalid TOTP produces a generic failure;
- valid TOTP generates a new recovery-code set;
- previous active recovery codes are revoked by the generation service;
- plain recovery codes are displayed once in the response;
- stored records contain only hashes;
- generation success and failure are logged as security events.

Why require the current TOTP code:

- recovery codes can later bypass the missing authenticator problem;
- creating new recovery codes is therefore a sensitive MFA lifecycle action;
- a fully authenticated session alone is not enough if the session was stolen after login;
- requiring the current TOTP code gives fresh proof that the user still controls the authenticator.

Security event policy:

- `totp_recovery_codes_generated` is recorded after a new set is created;
- `totp_recovery_codes_generation_failed` is recorded for invalid CSRF or invalid TOTP;
- the submitted TOTP code is never logged;
- generated recovery codes are never logged.

Code map:

- `src/Http/Controller/AccountSecurityController.php`
  - renders the generation form for active TOTP users;
  - `generateRecoveryCodes()` validates CSRF, verifies current TOTP, generates the set, and renders the one-time display.
- `public/index.php`
  - registers `POST /account/security/totp/recovery-codes/generate`;
  - wires `TotpLoginVerificationService`, `TotpRecoveryCodeService`, and security event logging.
- `src/Domain/Security/SecurityEventType.php`
  - adds `TotpRecoveryCodesGenerated`;
  - adds `TotpRecoveryCodesGenerationFailed`.
- `tests/Http/Controller/AccountSecurityControllerTest.php`
  - validates form rendering;
  - validates invalid-code failure;
  - validates successful generation and one-time display response;
  - validates security events without logging submitted codes.

What this does not implement yet:

- confirmation that the user saved the recovery codes;
- recovery-code entry during login;
- consuming a recovery code;
- resetting or disabling TOTP through recovery.

#### Step 3.5: Recovery Code Verification Foundation

This sub-step adds service-level recovery-code verification and consumption.

It still does not add a login recovery page. The goal is to make the core rule testable before connecting it to an HTTP recovery flow.

Expected behavior:

- load active recovery-code hashes for the target user;
- verify the submitted code against stored hashes;
- normalize submitted code input through the hasher;
- mark the matching recovery code as `used`;
- reject reuse of the same recovery code;
- reject codes owned by another user;
- return a generic success/failure result without exposing hashes or submitted values.

Why consume on successful verification:

- recovery codes are backup credentials;
- if a valid code remains active after use, it can be replayed;
- marking it as `used` makes recovery codes single-use.

Security implications:

- raw submitted recovery codes are never stored;
- failed verification does not reveal whether the submitted code matched another account;
- verification is scoped to the expected user id;
- HTTP rate limiting and recovery security events are still required before exposing this through a user-facing recovery route.

Code map:

- `src/Application/Totp/TotpRecoveryCodeService.php`
  - `TotpRecoveryCodeService::verifyAndConsume()` verifies one active code and marks it used.
- `src/Application/Totp/TotpRecoveryCodeVerificationResult.php`
  - carries generic success/failure without raw credential material.
- `tests/Application/Totp/TotpRecoveryCodeServiceTest.php`
  - validates successful verification and single-use consumption;
  - validates invalid-code rejection;
  - validates cross-user rejection.

What this does not implement yet:

- recovery-code form during login;
- recovery-code rate limiting;
- recovery security events in HTTP;
- resetting or disabling TOTP after recovery-code verification.
