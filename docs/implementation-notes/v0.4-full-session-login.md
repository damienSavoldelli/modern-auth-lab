# v0.4.0 Full Session Login Implementation Notes

This note reconstructs the `v0.4.0 - Full Session Login` milestone and its documentation follow-up patches from Git history, PRs, changelog, ADRs, and the tagged file tree.

The goal of this milestone was to complete the temporary password-only authenticated session flow before MFA enforcement.

## Learning Objective

At the end of this milestone, the project should make these concepts clear:

- why `password_verified` and `fully_authenticated` are different states;
- how protected routes enforce full authentication;
- why logout must be CSRF-protected;
- how initial rate limiting reduces online guessing;
- how security events make authentication decisions auditable;
- why this milestone is explicitly pre-MFA and temporary.

## Step 1: Full Session Login

This step completed a temporary password-only authenticated flow.

Important files:

- `src/Http/Controller/PasswordLoginController.php`
- `src/Http/Controller/AccountController.php`
- `src/Session/AuthSession.php`
- `src/Session/AuthSessionState.php`
- `tests/Http/Controller/PasswordLoginControllerTest.php`
- `tests/Http/Controller/AccountControllerTest.php`
- `docs/decisions/0010-full-session-login-without-mfa.md`

Behavior:

- successful password authentication marks the session as `fully_authenticated`;
- the user is redirected to `/account`;
- `GET /account` requires a fully authenticated session;
- anonymous or partial sessions cannot access the account page.

Why this was acceptable temporarily:

- the project needed a complete end-to-end password login before adding MFA;
- the milestone explicitly documented that this is pre-MFA behavior;
- later TOTP work replaces direct full login for users with active MFA.

Security implication:

- protected routes check the final authentication state;
- the state model remains ready for MFA even though MFA is not enforced yet;
- session rotation after authentication remains part of the login boundary.

## Step 2: Logout

Logout was implemented as a CSRF-protected unsafe action.

Important files:

- `src/Http/Controller/LogoutController.php`
- `tests/Http/Controller/LogoutControllerTest.php`

Behavior:

- `POST /logout` validates CSRF;
- valid logout destroys authentication session state;
- successful logout redirects away from protected content;
- invalid CSRF does not silently succeed.

Why POST instead of GET:

- logout changes server-side authentication state;
- GET requests should not perform state-changing actions;
- CSRF protection is meaningful on an unsafe method.

Security implication:

- another site should not be able to log a user out through an automatic image/link request;
- invalid logout attempts can later be logged as security events.

## Step 3: Initial Login Rate Limiting

This step introduced a small session-backed login rate limiter.

Important files:

- `src/Security/RateLimit/LoginRateLimiter.php`
- `tests/Security/RateLimit/LoginRateLimiterTest.php`
- `docs/decisions/0011-initial-login-rate-limiting.md`

Why rate limiting:

- password login is exposed to online guessing;
- generic errors reduce account enumeration but do not stop repeated attempts;
- even a simple limiter teaches where brute-force controls belong.

Initial design:

- session-backed limiter;
- small and local to the current app;
- no distributed storage;
- no IP reputation system;
- no user-facing lockout lifecycle.

Security tradeoff:

- session-backed limiting is useful pedagogically but not sufficient for multi-node production deployment;
- attackers can sometimes bypass session-local counters by changing clients;
- future production-grade rate limiting should use a shared backend and stronger keys.

## Step 4: Basic Security Events

This step added auditable security event persistence.

Important files:

- `src/Domain/Security/SecurityEventType.php`
- `src/Application/Security/SecurityEventLogger.php`
- `src/Infrastructure/Persistence/Migrations/CreateSecurityEventsTable.php`
- `src/Infrastructure/Persistence/SecurityEventRepository.php`
- `tests/Application/Security/SecurityEventLoggerTest.php`
- `tests/Infrastructure/Persistence/Migrations/CreateSecurityEventsTableTest.php`
- `tests/Infrastructure/Persistence/SecurityEventRepositoryTest.php`
- `docs/decisions/0012-basic-security-events.md`

Events introduced:

- password login success;
- password login failure;
- logout success;
- invalid logout CSRF attempt.

Why security events:

- authentication systems need observability;
- incidents cannot be investigated if decisions are invisible;
- later MFA, fallback, recovery, and Passkey events need the same logging pattern.

Security implication:

- events should describe the decision without logging secrets;
- password values, TOTP codes, CSRF tokens, and session ids must not be logged;
- event names should remain stable because downstream analysis depends on them.
