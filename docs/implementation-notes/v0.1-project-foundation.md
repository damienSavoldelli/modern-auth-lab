# v0.1.0 Project Foundation Implementation Notes

This note reconstructs the `v0.1.0 - Project Foundation` milestone from the Git tag, changelog, release content, and repository files.

The goal of this milestone was to establish a small but professional project base before implementing authentication behavior.

## Learning Objective

At the end of this milestone, the project should make these concepts clear:

- how to start a PHP project without a full framework;
- why `public/` is the web root;
- how Composer, PSR-4, PHPUnit, PHPStan, and PHP CS Fixer fit together;
- how Vite, vanilla JavaScript modules, Vitest, ESLint, and Prettier fit together;
- how to keep backend and frontend tooling independent but coordinated;
- why architecture and documentation rules should exist before security-sensitive code.

## Milestone Scope

Delivered scope:

- agent guidelines in `AGENTS.md`;
- project documentation structure;
- backend Composer tooling;
- frontend Vite tooling;
- initial PHP HTTP boundary;
- initial backend and frontend tests;
- quality scripts for formatting, static analysis, and test execution.

Out of scope:

- password authentication;
- sessions;
- CSRF protection;
- SQLite/libSQL persistence;
- TOTP;
- Passkeys/WebAuthn;
- trusted devices;
- recovery flows;
- CI/CD.

## Step 1: Project Rules And Documentation Discipline

The first step established the collaboration model before introducing sensitive authentication code.

Important files:

- `AGENTS.md`
- `docs/roadmap.md`
- `docs/architecture.md`
- `docs/security.md`
- `docs/auth-flows.md`
- `docs/concepts/passkeys.md`
- `docs/fallback-strategy.md`
- `docs/decisions/README.md`

Why this matters:

- authentication work becomes hard to audit when implementation starts before rules are explicit;
- a roadmap prevents accidental jumps from foundation work directly to complex MFA behavior;
- ADRs preserve the reasoning behind important architecture and security choices;
- agent rules reduce scope creep, unrelated refactoring, and unclear generated code.

Architecture implication:

- documentation is not treated as a side artifact;
- it is part of the engineering system used to control project direction.

Security implication:

- future decisions about sessions, MFA, fallback, and Passkeys can be tied back to documented assumptions instead of being hidden in code.

## Step 2: Backend Tooling Foundation

The backend was initialized around PHP 8.5+, Composer, strict typing, and PSR-4 autoloading.

Important files:

- `composer.json`
- `phpunit.xml.dist`
- `phpstan.neon.dist`
- `.php-cs-fixer.dist.php`
- `tests/Platform/PhpRuntimeTest.php`

Why Composer:

- it provides dependency management;
- it defines project scripts;
- it configures autoloading;
- it creates a predictable command surface for tests and analysis.

Why PHPUnit:

- backend behavior can be verified before security flows become complex;
- tests create a regression safety net for authentication state changes.

Why PHPStan:

- static analysis catches type and contract mistakes before runtime;
- it is especially useful in vanilla PHP because there is no framework container enforcing structure.

Why PHP CS Fixer:

- formatting and style stay consistent;
- code review can focus on behavior and security rather than style churn.

Code map:

- `tests/Platform/PhpRuntimeTest.php`
  - verifies that the runtime matches the expected PHP baseline.

Validation:

- `composer test`
- `composer analyse`
- `composer cs:check`

## Step 3: Frontend Tooling Foundation

The frontend was initialized with Vite and vanilla JavaScript modules.

Important files:

- `package.json`
- `vite.config.js`
- `vitest.config.js`
- `eslint.config.js`
- `.prettierrc.json`
- `.prettierignore`
- `assets/js/main.js`
- `assets/css/main.css`
- `tests/frontend/main.test.js`

Why vanilla JavaScript first:

- the first version should teach browser behavior without introducing SPA complexity;
- WebAuthn and Passkeys can later be added with clear browser APIs;
- TypeScript remains planned for a later milestone, once the frontend boundaries are clearer.

Why Vite:

- it gives a modern development and build workflow;
- it supports ES modules naturally;
- it prepares the project for future frontend tests and TypeScript migration.

Why native CSS:

- early UI work remains readable;
- the project avoids framework-specific styling complexity too soon;
- PostCSS or other CSS tooling can be introduced later only if it provides clear value.

Validation:

- `npm run build`
- `npm test`
- `npm run lint`
- `npm run format`

## Step 4: Minimal HTTP Foundation

The first HTTP boundary was intentionally small.

Important files:

- `public/index.php`
- `src/Http/Router.php`
- `src/Http/Response.php`
- `tests/Http/RouterTest.php`
- `tests/Http/ResponseTest.php`

Implemented behavior:

- `public/index.php` is the front controller;
- `GET /health` returns a diagnostic JSON response;
- `Router` maps method and path pairs to handlers;
- `Response` represents HTTP status, headers, and body.

Why `public/` matters:

- production servers should expose only public assets and the front controller;
- application source, dependencies, docs, local databases, and environment files should not be web-accessible;
- this keeps the deployment model compatible with Apache, Nginx, and PHP's local development server.

Security implication:

- even before login exists, the project establishes the boundary that protects internal files from direct HTTP access.

Architecture implication:

- the front controller owns HTTP entry;
- the router owns dispatch;
- response objects own output details;
- later controllers can be added without turning `public/index.php` into business logic.

## Step 5: Initial Tests And Quality Checks

The milestone included both backend and frontend tests from the beginning.

Backend tests:

- `tests/Http/RouterTest.php`
- `tests/Http/ResponseTest.php`
- `tests/Platform/PhpRuntimeTest.php`

Frontend tests:

- `tests/frontend/main.test.js`

Why this matters:

- tests are not added after the authentication system is already complex;
- the project establishes the habit of validating each step;
- the first tests are intentionally small because the behavior is still small.

## Design Tradeoffs

Tradeoff: vanilla PHP instead of a framework.

- Benefit: every authentication and security decision remains visible.
- Cost: the project must define its own structure carefully.

Tradeoff: minimal HTTP layer instead of full middleware stack.

- Benefit: the first boundary is easy to understand.
- Cost: middleware concerns such as sessions and CSRF come later.

Tradeoff: vanilla JavaScript first.

- Benefit: WebAuthn browser APIs can later be learned directly.
- Cost: stronger frontend typing is deferred to `v1.1`.

## What This Milestone Enables

`v0.1.0` enables later milestones to add security features in a controlled order:

1. session and CSRF primitives;
2. persistence;
3. users and password verification;
4. full session login;
5. TOTP enrollment and challenge;
6. Passkeys/WebAuthn;
7. recovery and trusted devices;
8. CI/CD and mutation testing.
