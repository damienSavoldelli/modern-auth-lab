# 0018 - TOTP Recovery Strategy

## Status

Accepted

## Context

TOTP is now an enforced second factor for users with an active TOTP credential.

Normal TOTP disable is available when the user still controls the authenticator app. That flow requires the current TOTP code and revokes the active credential only after possession is proven.

The harder case is lost-authenticator recovery:

- the user may have lost the phone;
- the user may have deleted the authenticator entry;
- the user may have replaced the device without transferring the secret;
- the server receives no notification from the authenticator app when any of this happens.

The server only knows its own credential state. It cannot know whether the authenticator entry still exists locally on the user's device.

Using password-only recovery would weaken MFA because an attacker with the password could remove the second factor.

## Decision

The project will treat TOTP recovery as a separate, stricter flow than normal TOTP disable.

For the first self-service recovery mechanism, the project will introduce recovery codes.

Recovery codes must be:

- generated by the server;
- shown to the user only once;
- stored only as hashes;
- single-use;
- revocable;
- auditable through security events;
- rate-limited when submitted.

Normal TOTP disable remains the preferred low-friction path when the user still has the authenticator app.

Lost-authenticator recovery must not silently bypass MFA. It must require a valid recovery code or a future stronger recovery policy.

This milestone may introduce the recovery-code foundation without completing every future product workflow such as email delivery, notification delays, trusted-device assisted recovery, or admin-assisted recovery.

## Consequences

The project keeps two separate concepts:

- TOTP disable: user still controls the current authenticator and proves it with a TOTP code.
- TOTP recovery: user cannot provide the current TOTP code and must use a pre-established recovery method.

Recovery codes become security-critical credentials.

Recovery code storage must follow password-like rules:

- never store raw recovery codes;
- hash submitted codes before comparison;
- never log submitted codes;
- consume or revoke a code after successful use.

The user must receive recovery codes before they lose access to the authenticator. If no recovery method exists, the project must fail closed until a later recovery policy is implemented.

Security events must distinguish recovery from normal disable so account history remains auditable.

## Rejected Alternatives

Password-only TOTP reset was rejected because it turns MFA into a password-only control when the account is under stress.

Email-only OTP recovery was deferred because email delivery infrastructure, mailbox compromise risk, delivery reliability, and rate limiting would introduce a separate recovery channel before the current project is ready for it.

SMS recovery was rejected for this stage because SMS is vulnerable to SIM swap, telecom account compromise, and delivery weaknesses.

Trusted-device assisted recovery was deferred because trusted devices are a later roadmap milestone and should not be invented implicitly here.

Admin/manual recovery was deferred because it requires identity proofing, operational procedures, and abuse handling outside the current local lab scope.
